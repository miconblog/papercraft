## 배경

사용자 요청(2026-09-09). **게임을 만들며 겪은 것을 공방 일지로 남겨 사이트에
게시하고 싶다.** 지금 이 사이트에는 글을 담을 자리가 없다 — 게임 카탈로그와
에디터, 인쇄뿐이다.

이 사이트의 게임은 전부 "옛 인쇄본을 다시 그린 것"이라 만드는 과정에 이야기가
있다(`IDE-015`의 로빈슨 도법 지도, `IDE-018`의 무게중심 잡기, `IDE-021`의 눈·코를
어떻게 뽑았나). 그 이야기가 사람을 데려오는 유일한 밑천이기도 하다 — `IDE-013`을
붙여 놓고 보니 홍보가 없으면 유입도 없다.

## 글은 관리자 화면에서 쓴다

**2026-09-09 사용자 결정.** 저장소에 마크다운 파일을 커밋하는 쪽이 만들 것이
훨씬 적지만, 컴퓨터 앞에서만 글을 쓸 수 있다. 브라우저에서 쓰면 폰으로도
쓰고 고칠 수 있다.

값은 `IDE-013`이 세운 `daddys_craft` 스키마에 둔다. `IDE-022`가 게임 오픈일로
같은 일을 하므로, **표를 만들고 여는 규약도 시각 판정도 그 이슈와 나눠 쓴다** —
예약 게시는 예약 공개와 같은 문제다.

## 본문을 어떤 형식으로 담나

마크다운이 자연스럽다 — 이 저장소의 문서가 전부 마크다운이고 사용자가 이미
그 문법에 익숙하다.

**그런데 마크다운을 HTML 로 그리는 순간 XSS 가 생긴다.** 글을 쓰는 사람이
관리자 하나뿐이라 "누가 나쁜 것을 넣겠나" 싶지만, 관리자 세션은 비밀번호
하나로 지켜지고(`IDE-013`) 그게 새면 사이트 전체에 스크립트를 심을 수 있는
길이 된다. 그리는 쪽에서 막아야 한다.

정할 것: 마크다운 라이브러리와 정화(sanitize) 방식, 그리고 **저장할 때 한 번
HTML 로 바꿔 두느냐 읽을 때마다 그리느냐**. 뒤쪽이 고치기 쉽고 앞쪽이 빠르다.

## 사진을 어디에 두나

공방 일지에는 사진이 들어간다 — 종이로 뽑아 접은 것, 아이가 놀고 있는 것.
후보는 Supabase Storage 와 저장소 안 `public/`이었다. **2026-09-09 사용자가
Storage 를 골랐다** — `public/`은 아무것도 안 세워도 되지만 사진을 넣을 때마다
컴퓨터 앞으로 돌아가야 해서, 관리자 화면을 고른 이유가 반쪽이 된다.

같은 날 **아이 얼굴이 나온 사진도 올린다**고 정했다(사용자 선택: "추측 불가
주소"). 그래서 공개 버킷을 쓰되 파일 이름 앞에 임의 문자열 32자를 붙인다.

## 공개 쪽 화면

- 목록과 글 하나 — 경로는 **`/blog`** 다(2026-09-09 사용자 결정)
- 홈에서 최근 글로 들어가는 길. 홈은 지금 히어로 → 아이와 함께 → 만드는 순서 →
  게임 목록이다. **글이 게임을 밀어내지 않는 자리**를 찾는다
- `sitemap`·OG 메타데이터. 글은 검색으로 들어오라고 쓰는 것이라 이게 빠지면
  쓴 보람이 없다
- 방문 통계는 저절로 잡힌다 — `PageViews`가 루트 레이아웃에 있어 새 경로도 센다

  정화 방식, 저장할 때 바꿔 두느냐 읽을 때마다 그리느냐"였는데, **셋째 답을
  골랐다** — 마크다운에서 React 엘리먼트를 바로 만든다(`lib/blog/markdown.tsx`).
  - `marked` + `DOMPurify` 는 씻는 규칙이 한 칸만 틀려도 스크립트가 지나가는
    자리가 남고, 서버에서 돌리려면 jsdom 까지 따라온다. 엘리먼트로 만들면
    `dangerouslySetInnerHTML` 이 코드에 없어서 **마크업이 될 길 자체가 없다.**
    유지보수할 정화 규칙도 사라진다.
  - 잃는 것은 문법의 폭이다(표·각주·중첩 목록이 안 된다). 쓰는 사람이 한 명이고
    필요한 것이 제목·문단·강조·목록·인용·코드·링크·사진이라 그 선에서 끊었다.
  - 스스로 막는 곳은 **주소 한 군데**다. React 도 `href="javascript:…"` 는 막아
    주지 않는다. 허용 목록(`http`·`https`·`mailto`·상대 주소)을 벗어나면 링크로
    만들지 않고 글자로 남긴다 — 지워 버리면 글쓴이는 왜 사라졌는지 모른다.

  문제를 고친 뒤 사용자가 물었다 — "미리보기는 관리자만 보면 되니까 관리자 라우터
  하위로 옮기는 건 어때?" 맞는 말이라 옮겼다(`/admin/posts/<id>/preview`).
  얻은 것이 셋이다.
  - **쿠키가 반드시 닿는다.** 경로 문제가 아예 생길 수 없는 자리다. 앞의 자동
    복구는 게임 미리보기(`IDE-022`)를 위해 남겨 둔다 — 그쪽은 여전히 공개
    주소에서 실물을 봐야 한다.
  - **초안이 공개 주소에 존재하지 않는다.** 문지기의 관리자 우회를 걷어내
    `/blog/<슬러그>` 가 **누구에게나 같아졌다.**
  - 그 덕에 **공개 화면이 스스로도 검사할 수 있게 됐다**(`openPost`). 전에는
    관리자를 통과시켜야 해서 못 했다 — 관리자인지 알려면 쿠키를 읽어야 하고,
    읽으면 정적 렌더링이 깨진다. 이제 문지기가 matcher 실수로 사라져도 안 낸
    글은 새지 않는다.
  - 그리는 것은 공개 화면과 **같은 컴포넌트**(`PostArticle`)다. 두 벌로 두면
    미리 본 것과 나가는 것이 어긋나 미리 본 뜻이 없다.
  - 쓰이지 않게 된 `isPostVisible`(`IDE-022` 의 `isGameVisible` 을 흉내 낸
    것)은 지웠다. 글에는 도안 바이트가 나가는 API 가 없어 애초에 부를 데가 없었다.
- **2026-09-09 — 미리보기 404 의 진짜 원인은 쿠키 경로였다**(사용자 신고).
  `IDE-022` 가 인증 쿠키를 `/admin` → `/` 로 넓혔지만 그것을 **로그인·로그아웃
  에서만** 했다. 그 전에 로그인한 브라우저는 쿠키가 옛 경로에 갇혀 있어,
  **관리자 화면은 멀쩡히 열리는데 `/games/<id>`·`/blog/<슬러그>` 미리보기만
  404** 가 난다 — 그 요청에 쿠키가 안 실려 문지기가 남으로 본다. 로그인은 돼
  있으니 사람 쪽에서는 무엇이 잘못됐는지 알 길이 없다.
  - 문지기가 **관리자 화면을 열 때마다 같은 값을 `/` 에 다시 심는다.** 한 번
    열면 저절로 낫고, 이미 새것이면 같은 것을 덮어쓸 뿐이다.
  - **옛 경로 것은 지우지 않는다.** `NextResponse.cookies` 가 이름만 보고
    덮어써서, 심기와 지우기를 나란히 두면 **지우기만 나가고 세션이 통째로
    날아간다**(고치다 실제로 그렇게 만들었다). 남겨 두어도 값이 같아 어느 쪽이
    읽혀도 결과가 같고, 다음 로그아웃·로그인 때 지워진다.
- **2026-09-09 — 공방 일지에 자기 404 를 준다**(사용자 지적). 사이트의 404 는
  "없는 **게임**일 수 있다 · **게임 목록**으로"라고 말한다. 글을 찾다 온 사람에게
  맞지 않는 안내다. `app/blog/not-found.tsx` 를 두되 **안 낸 글과 없는 주소가
  같은 화면**이어야 한다는 규칙은 그대로다 — 다르면 그 차이가 "여기 안 낸 글이
  있다"는 신호가 된다.
- **2026-09-09 — 이름은 「공방 일지」다**(사용자 결정). 「제작일지」로 쓰고 있던
  것을 바꿨다. 사이트 이름이 "아빠 공방"이라 **글이 어디서 나온 것인지가 이름에
  들어간다** — 「제작일지」는 무엇을 만드는 곳인지 말해 주지 않는다. 주소는
  `/blog` 그대로다(영문 슬러그라 이름과 따로 논다).
- **2026-09-09 — 슬러그를 못 뽑아도 막지 않는다.** 사용자가 한국어로 쓰므로 제목에서
  슬러그를 뽑으면 대부분 빈 값이 된다. 그때 "영문 주소를 적으세요"로 막으면 폰에서
  쓰다가 걸린다. `post-20260909-a3f1` 처럼 날짜로 만들어 두고, 그 값이 화면에
  그대로 보이니 내기 전에 고치면 된다.
