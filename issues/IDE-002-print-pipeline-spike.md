## 배경

이 제품의 가치는 "화면에서 예쁘다"가 아니라 **종이에 원하는 치수로 정확히 나온다**에
있다. 도안이 몇 mm씩 어긋나면 게임판으로 못 쓴다.

원본 게임판은 **운동장이 딱 A4 크기**였고, 좌우 점수/주사위 트랙과 하단 게임 방법이
그 바깥을 프레임처럼 둘러싸서 종이는 A4보다 조금 컸다. 여기서 세 가지가 정해졌다
(2026-09-03):

- **기준 크기는 원본** — 배율 100%에서 운동장이 210×297mm다
- **배율은 사용자가 고른다** — 아이와 크게 놀고 싶으면 확대, 휴대하려면 축소.
  확대하면 A4 여러 장에 나눠 뽑아 붙인다
- **핵심 게임판과 부속을 분리해 뽑는다** — 점수/주사위 트랙, 게임 방법 같은 프레임
  요소는 오림용 별지로 뺀다. 그래서 보드 시트에는 운동장만 남는다

즉 **타일 분할은 선택 기능이 아니라 필수**다. 렌더링 방식에 따라 이후 에디터와
내보내기 구현이 통째로 달라지므로, 코드를 쓰기 전에 실제 출력으로 검증한다.

## 할 일

- [x] 후보 비교 — ① CSS `@page` + 브라우저 인쇄 ② SVG → PDF 생성 ③ Canvas 래스터 후 PDF 임베드
  - **②를 채택**했다(`pdf-lib`로 벡터 PDF 생성, 글자는 벡터 윤곽선). ①은 사용자 인쇄 설정이 치수를 말없이 바꾸고, ③은 A4 한 장이 300dpi에서 25.5MB·600dpi는 180초 안에 생성조차 못 했다
- [ ] ⚠︎ 각 후보로 10cm 눈금자가 그려진 테스트 도안을 만들어 A4로 실제 출력하고 자로 오차 측정
  - 검증 도안 3종(보드·부속 별지·인쇄 가능 영역 탐침)과 후보별 산출물을 만들고 **Ghostscript 600dpi 실측**(정밀도 ≈0.01mm)까지 끝냈다 — 채택안 오차 ±0.006mm
  - **남은 것: 종이 출력과 자 실측.** 이 환경에 프린터가 없다. 절차는 `spikes/print-pipeline/README.md` 2·3절
- [ ] ⚠︎ 배율 정확도 검증 — 50% · 100% · 200%로 뽑아 각각 지정한 치수대로 나오는지 측정
  - 디지털 실측은 세 배율 모두 통과 — 50% ±0.009mm · 100% ±0.006mm · 200% ±0.008mm. `pdf-lib`의 페이지 상자는 210.000×297.000mm로 정확했다
  - **남은 것: 종이 실측**(위와 같은 이유)
- [x] **가정용 프린터 여백 문제 확인** — 운동장이 210×297mm면 A4 용지와 같은 크기라 인쇄 불가 여백에 걸린다. 무여백 인쇄 지원 현황을 보고, 100%에서 보드 시트를 A4 한 장으로 낼 수 있는지 / A4 두 장 분할이 기본이어야 하는지 결론 낸다
  - **A4 두 장이 기본이다.** 무여백은 레이저에 사실상 없고, 잉크젯 무여백은 가장자리를 채우려 이미지를 몇 % 확대해 ±1mm를 스스로 깬다. 사용자가 자기 프린터 여백을 잴 수 있게 탐침 시트(`B2-probe-printable-area.pdf`)를 만들었고, "A4 한 장 맞춤(≈94%)"은 100%가 아님을 밝힌 별도 프리셋으로 둔다
- [x] 타일 분할 규격 정의 — 겹침 폭 · 재단선 · 조립 표식 · 장 번호
  - 겹침 10mm · 여백 6mm · 용지 방향 자동 선택 · 도안 가운데 정렬. 장당 도안 길이는 `c = (L + (n-1)V)/n`로 **균등 분배**한다(마지막 장에 몰아주면 겹침이 100mm까지 벌어진다). 규격은 `docs/print-spec.md` §5
- [ ] ⚠︎ 실제로 확대 출력해 붙였을 때 필드 라인이 이어지는지 확인
  - 200% 8장의 이음 11곳 전부 **정합 오차 0.000mm**(300dpi 1픽셀 = 0.085mm), 계획대로 이어 붙인 뒤 잰 치수도 ±0.2mm 안
  - **남은 것: 실제로 뽑아 붙여 보기** — 종이 신축과 재단 오차는 실물에서만 나온다
- [ ] ⚠︎ 브라우저별 차이 확인(Chrome · Safari · Firefox)과 사용자 인쇄 설정이 결과를 흔드는 정도 기록
  - **인쇄 설정 영향은 수치로 잡았다** — 200%(420×594mm) 시트를 A4로 뽑게 두니 경고 없이 **정확히 절반**으로 줄었다(A↔B 300mm → 150.03mm). 채택안은 PDF를 코드가 만들어 이 경로를 없앤다
  - **남은 것: Safari·Firefox 실기 확인.** Chrome만 이 환경에 있다. 확인표는 `spikes/print-pipeline/README.md` 6절
- [x] 부속 별지의 오림선·접는선을 인쇄로 표현하는 방법 확인
  - 오림선 실선 0.25mm · 골접기 파선(2/1.5mm) · 산접기 일점쇄선 · 풀칠면 45° 해칭으로 규약을 정하고 `B2-accessory-tiled-100.pdf`로 렌더까지 확인했다. 색에 의존하지 않아 흑백에서도 넷이 구분된다. 같은 시트에 0.05~0.4mm 굵기 눈금을 넣어 기종별 최소 선 굵기를 잴 수 있게 했다(⚠︎ 실제 하한은 종이 실측에서 확정)
- [x] 한글 폰트 임베딩 방식과 결과 파일 용량 확인 (도안에 한글 라벨이 많다)
  - **폰트를 임베딩하지 않고 벡터 윤곽선으로 그린다.** `pdf-lib`의 한글 CID 임베딩은 Ghostscript·macOS 미리보기 양쪽에서 깨졌고, 윤곽선은 둘 다 정상이면서 파일도 더 작다(25.2KB vs 44.7KB, 전체 임베딩은 3.7MB)
- [x] 산출 규격을 한 페이지로 정리해 `IDE-007`이 그대로 따르게 한다
  - [`docs/print-spec.md`](../docs/print-spec.md). 좌표계·기준 크기·채택안과 탈락 사유·여백·타일 규격·부속 표기·폰트·검증 수치·브라우저 안내·`IDE-007` 인계 목록

## 결정 기록

- 2026-09-03 · 초기에 "B2 지원"으로 적었으나 착오였다. B2는 500×707mm로 A4의 약
  5.7배인 포스터 크기다. 실제 원본은 A4보다 조금 큰 스케치북이었고 그 위에서
  **운동장이 A4**였다. B2는 요구사항에서 제외한다.
- 2026-09-03 · "전체 도안을 A4 한 장에" 안은 폐기했다. 프레임까지 A4에 넣으면
  운동장이 약 150×210mm로 줄어 아이와 놀기에 너무 작다.
- 2026-09-03 · 기준 크기는 원본(운동장 A4)으로 하되 **배율은 사용자가 자유롭게**
  고르고, **핵심 게임판과 부속을 분리 출력**한다. 이 결정으로 타일 분할이 필수가 됐다.
- 2026-09-04 · **채택: 도안 → 코드가 만든 벡터 PDF(`pdf-lib`), 글자는 벡터 윤곽선.**
  규격은 [`docs/print-spec.md`](../docs/print-spec.md), 검증 도구는
  [`spikes/print-pipeline/`](../spikes/print-pipeline/README.md)에 있다.
  - **탈락 ① CSS `@page` + 브라우저 인쇄** — 도안 자체는 정확하지만(±0.016mm) 결과를
    사용자의 인쇄 대화상자가 정한다. 200%(420×594mm) 시트를 A4로 뽑게 두니 경고 없이
    **정확히 절반**으로 줄었다(A↔B 300mm → 150.03mm). 제품의 핵심 가치를 우리가
    통제하지 못하는 설정에 걸 수 없다. Chrome이 만든 PDF는 페이지 상자도 0.1~0.2mm
    반올림된다(210mm 요청 → 209.89mm).
  - **탈락 ②-a jsPDF + `svg2pdf.js`** — 치수는 채택안과 같게 정확하지만 브라우저에서만
    돌아 서버 생성이 안 되고, 한글을 내려면 폰트를 굵기마다 브라우저에 등록해야 한다.
    Regular만 등록했더니 본문은 멀쩡하고 굵은 제목만 조용히 깨졌다. TTF 9.9MB를 실어야
    했고 한 장 생성에 17.5초 걸렸다.
  - **탈락 ③ Canvas 래스터 후 PDF 임베드** — A4 한 장이 150dpi 6.4MB · 300dpi 25.5MB,
    600dpi와 200%/300dpi는 **180초 안에 생성조차 못 했다**. 같은 도안이 벡터로는 25KB다.
- 2026-09-04 · **한글은 폰트를 임베딩하지 않고 벡터 윤곽선으로 그린다.** `pdf-lib`의
  CID 임베딩은 Ghostscript와 macOS 미리보기 양쪽에서 깨졌다. 더 나쁜 것은 재현이
  불안정하다는 점이다 — 다섯 줄짜리 표본은 미리보기에서 정상인데 같은 코드로 만든
  실제 도안은 깨졌다. 윤곽선은 두 뷰어 모두 정상이고 파일도 더 작다(25.2KB vs 44.7KB).
  대신 PDF에서 글자 선택·검색이 안 되는데, 게임판에는 문제가 되지 않는다.
- 2026-09-04 · **100% 보드 시트는 A4 2장이 기본이다**(가로 보드 297×210은 A4 세로
  2장, 세로 보드 210×297은 A4 가로 2장). 운동장이 A4와 같은 크기라
  100%에서는 반드시 인쇄 불가 여백에 걸린다. 무여백 인쇄로 피하지 않기로 했다 —
  레이저에는 사실상 없는 기능이고, 잉크젯의 무여백 모드는 가장자리를 채우려 이미지를
  몇 % 확대해 우리가 지키려는 ±1mm를 스스로 깬다. A4 한 장에 담고 싶은 사용자를 위해
  "A4 한 장 맞춤(≈94%)"을 두되 100%가 아님을 UI에 밝힌다.
- 2026-09-04 · 타일 분할은 **겹침을 뺀 나머지를 균등 분배**한다(`c = (L + (n-1)V)/n`).
  처음에는 마지막 장에 남는 만큼 몰아주게 짰는데, 100% 보드에서 겹침이 10mm가 아니라
  99mm로 벌어졌다. 겹침이 장마다 다르면 붙이는 사람이 헷갈리고 종이도 버린다.
- 2026-09-04 · 스파이크에서 잡은 렌더러 버그 두 개를 기록해 둔다. `IDE-007`이 같은
  함정을 다시 밟지 않게 하려는 것이다.
  - SVG에서 **클립과 변환을 같은 `<g>`에 걸면 안 된다.** SVG는 요소의 `transform`이
    적용된 좌표계에서 `clip-path`를 해석해서, 잘리는 자리가 도안과 함께 밀려난다.
    클립은 변환 없는 바깥 `<g>`에 건다.
  - `pdf-lib`의 `drawRectangle`은 `borderColor`를 주면 `color`를 지정하지 않는 한
    **칠하지 않는다.** 칠과 테두리를 각각 명시해야 한다.
- 2026-09-04 · 보드 방향은 `IDE-003`이 **297×210mm 가로**로 확정했다. 이 이슈는
  "운동장 = A4 한 장"까지만 정했었는데, 규격이 방향에 중립적이라 문제가 없었다 —
  타일 계산이 파트 치수를 그대로 받고 세로든 가로든 100%는 A4 2장이다. 검증 도안은
  세로로 만들었지만 결론은 양쪽에 적용된다.
- 2026-09-04 · `doing` → `blocked`. **종이 실측을 기다린다.** 이 환경에 프린터가 없어
  수용 기준 6개 중 3개(100% 실측 · 50%/200% 실측 · 타일 붙여 이음 확인)를 채울 수 없다.
  나머지는 전부 끝났고 디지털 실측(정밀도 ≈0.01mm)으로는 모두 통과했다. 사람이 할
  일은 `spikes/print-pipeline/README.md`의 체크리스트에 순서대로 적혀 있다 —
  ① 인쇄 가능 영역 탐침 ② 100% 실측 ③ 축소·확대 실측 ④ 타일 붙여 이음 확인
  ⑤ 부속 별지 오리고 접어 보기 ⑥ Safari·Firefox 확인. 결과를 받으면 곧바로 `review`로
  넘길 수 있다.
