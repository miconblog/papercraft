## 배경

사용자 요청(2026-09-13). "각 게임 페이지 하단에 댓글과 공유하기 기능을 넣고
싶어."

지금까지 이 사이트는 **한 방향**이었다. 주인이 도안을 올리고 글을 쓰고, 오는
사람은 뽑아 간다. 만들어 본 사람이 무언가 말할 자리가 없고, 남에게 알릴 길도
없었다 — `/admin/share` 의 링크 만들기는 **주인이 쓰는 도구**다(`IDE-013`).

## 무엇을 지켜야 하나

이 이슈는 저장소에서 처음으로 **남이 보낸 값을 담고, 그것을 남에게 보여 준다.**
앞선 이슈들이 지켜 온 것 가운데 여기서 무너지기 쉬운 것이 셋이다.

1. **본문이 HTML 문자열을 거치지 않는다** — `IDE-023`·`IDE-028` 이 가장 공들인
   자리다. 댓글은 쓰는 사람이 주인이 아니므로 **한 걸음 더 좁힌다**: 마크다운도
   해석하지 않는다. 줄바꿈만 CSS 로 살린다.
2. **Supabase 가 꺼져도 사이트는 뜬다** — 댓글은 곁붙이라 못 읽으면 그 칸만
   빈다. 쓰기는 반대로 **실패를 반드시 보여 준다**(조용히 사라진 댓글은 쓴 사람이
   승인을 기다리는 것으로 오해한다).
3. **오픈 전 게임과 안 낸 글은 없는 것처럼 군다** — `IDE-022`·`IDE-023` 의
   문지기는 **화면**을 막는다. 서버 액션은 URL 만 알면 밖에서 부를 수 있어서,
   대상이 열려 있는지를 액션이 스스로 한 번 더 본다.

## 무엇을 고르나

**자체 DB + 익명 닉네임 + 관리자 승인제**(2026-09-13 사용자 결정). 공유는
**다섯 수단 전부** — 카카오톡 · 시스템 공유 · X · 페이스북 · 링크 복사. 붙는 곳은
**게임 화면과 공방 일지 글** 둘이다.

Giscus(GitHub 로그인)와 Disqus 도 후보였다. 고르지 않은 이유는 결정 기록에 적었다.

## 수용 기준

- [x] 게임 화면과 글 화면 아래에 **같은 모양**의 공유 줄과 댓글 칸이 선다
- [x] 이름을 비우고도 댓글을 쓸 수 있다 — `이름 없음` 으로 들어간다
- [x] 쓴 댓글이 **화면에 나타나지 않고**, 그 이유를 폼이 말해 준다 —
      "확인한 뒤에 올려 둘게요"
- [x] 관리자 화면에서 승인하면 그 게임·글 페이지가 곧바로 다시 그려진다 —
      `updateTag(commentsTag(…))`. 남의 페이지는 깨우지 않는다
- [x] 승인을 되돌리면 화면에서 사라지고 대기 목록으로 내려온다
- [x] 본문의 `<script>` 와 `**굵게**` 가 **글자 그대로** 나온다 — 공개 화면과
      관리자 화면 양쪽에서 그렇다
- [x] Supabase 가 꺼져 있어도 게임 화면과 글이 그대로 뜬다 — 댓글 칸은 "아직
      댓글이 없습니다"이고 쓰는 칸은 열린다. 보낼 때 **무엇을 고쳐야 하는지**
      알려 준다(환경변수 이름까지)
- [x] 데스크톱에 눌러도 아무 일 없는 버튼이 없다 — 시스템 공유는
      `navigator.share` 가 있을 때만, 카카오톡은 키가 있을 때만 선다
- [x] 공유 링크에 붙은 utm 이 표의 **소셜** 칸으로 들어간다 — 수집 쪽과 **같은
      함수**(`channelOf`)로 시험이 확인한다
- [x] 복사가 막힌 브라우저(https 아님)에서도 주소를 얻을 수 있다 — 꺼내 놓고
      골라 준다
- [x] 공유 줄이 공방 일지 글의 목차에 끼어들지 않는다 — 제목이 아니라 이름 붙은
      묶음(`role="group"`)이다
- [x] 빌드가 게임 화면을 여전히 **정적으로** 낸다(`● /games/soccer`, 1m 재검증)
- [x] 운영 저장소에 표가 실제로 서 있고 앱이 쓰는 길로 닿는다 — PostgREST 로
      `comments` 를 읽어 200 을 받았다(빈 표)
- [ ] ⚠︎ **오픈 전 게임·안 낸 글에 액션을 직접 불러도 안 담긴다** — 코드로는
      막았고(`targetIsOpen`) 시험은 각 판정 모듈에 있지만, **밖에서 직접 부르는
      확인은 남았다**
- [ ] ⚠︎ **카카오톡 카드가 실제로 뜬다** — 키와 도메인 등록이 없어 확인하지
      못했다. 키가 없는 지금은 버튼도 SDK 도 없다
- [ ] ⚠︎ **폰에서 시스템 공유 시트가 열린다** — 이 저장소엔 브라우저 도구가 없다
- [ ] ⚠︎ **도배 제한이 실제로 걸린다** — 해시 비밀값이 있는 환경에서 열 개를
      연달아 보내 봐야 안다

## 결정 기록

- **2026-09-13 — 자체 DB 에 담고 익명으로 쓴다**(사용자 결정). Giscus 는 구현이
  가장 가볍지만 **댓글을 쓰려면 GitHub 계정이 필요하다** — 아이와 종이 게임을
  뽑는 사람에게 낼 수 있는 문턱이 아니다. Disqus 는 검토·스팸·알림을 다 대신해
  주지만 **방문자 데이터가 외부로 나가고 광고·추적 스크립트가 실린다**. 분석을
  직접 만든(`IDE-013`) 이 프로젝트의 방향과 정반대라 고를 수 없었다.
  - 대가는 분명하다. 스팸 대비와 검토 화면을 **직접 만들어야 한다.**
- **2026-09-13 — 승인 후 공개**(사용자 결정). 관리자가 1명뿐인 사이트에서
  답이 늦어지는 것이 대가다. 얻는 것은 **노출 사고가 0** 이라는 것 —
  아이들이 보는 화면에 무엇이 잠깐이라도 걸릴 여지를 남기지 않는다.
  - 그래서 **쓴 사람에게도 안 보인다.** 자기 댓글만 보여 주는 길(쿠키로 표시)도
    있지만, 그러면 "내 것은 보이는데 남의 것은 안 보인다"가 되어 몇 개가 달렸는지
    오해하게 된다. 대신 폼이 **승인제라는 것을 미리 말한다.**
- **2026-09-13 — 내리는 스위치를 따로 두지 않았다.** `posts` 는 `publish_at` 과
  `hidden` 을 함께 두었다(`IDE-022`·`IDE-023`). 댓글에서는 **승인을 되돌리면 대기로
  돌아가고, 그것이 내리는 것과 같은 효과**다. 뜻이 겹치는 스위치가 둘이면 급할 때
  어느 것을 눌러야 하는지 헷갈린다.
- **2026-09-13 — 글은 슬러그가 아니라 `id` 로 가리킨다.** 슬러그는 주인이 편집
  화면에서 고칠 수 있는 값이라, 한 번 고치면 달린 댓글이 **전부 미아**가 된다.
  게임은 반대로 `id` 가 코드에 박힌 등록소의 값이라 그것이 가장 안전하다.
- **2026-09-13 — 댓글은 대상별로 묻는다**(글 목록과 반대다). `posts.ts` 는 표를
  통째로 받아 화면이 고른다 — 글이 수십 편 규모이고 캐시 항목을 하나로 두는 값이
  있었다. 댓글은 **대상 수 × 사람 수**로 늘어나므로 통째로 받으면 게임 하나를 열
  때 사이트 전체의 댓글이 따라온다.
  - 캐시 태그도 대상별이다. 뭉쳐 두면 댓글 한 개를 승인할 때 사이트의 모든
    게임·글 페이지가 함께 다시 그려진다.
- **2026-09-13 — 승인 거르기를 SQL 에 맡겼다.** 받아 놓고 앱에서 거를 수도 있지만,
  그러면 **대기 중인 댓글의 본문이 페이지를 그리는 서버까지 넘어온다.** 언젠가
  누군가 그것을 화면에 흘린다. 아예 안 받는 편이 단단하다.
- **2026-09-13 — 쓰기 액션이 대상이 열려 있는지 스스로 본다.** 화면에 폼이 안
  보이는 것은 아무것도 막아 주지 않는다 — 서버 액션은 URL 만 알면 밖에서 그대로
  부를 수 있다. 판정은 **각 판정 모듈에게 묻는다**(`isOpen` · `isPublished`).
  규칙을 베껴 쓰면 오픈 규칙이 바뀔 때 이곳만 옛 규칙으로 남는다.
  - **관리자 우회를 두지 않았다.** 미리보기에서 댓글을 달 이유가 없고, 우회가
    있으면 "오픈 전에는 댓글이 없다"가 조건부 참이 된다.
- **2026-09-13 — 도배 제한에 `IDE-013` 의 방문자 해시를 쓴다.** 날마다 도는 salt
  를 키로 쓴 HMAC 이라 **IP 도 UA 원본도 남지 않고**, 하루가 지나면 같은 사람도
  다른 값이 된다. 그 회전 주기가 제한의 창(10분)보다 훨씬 길어서 충분하다.
  - 비밀값을 읽는 함수를 `analytics/config.ts` 에 따로 뒀다(`hashSalt`).
    `analyticsConfig` 는 `ANALYTICS_ENABLED` 를 보는데, 그것에 묶으면 **수집을
    끄는 순간 도배 제한도 함께 풀린다** — `supabaseConnection` 이 같은 이유로 같은
    선택을 했다.
  - 한도는 10분에 5개로 넉넉하다. 아이와 번갈아 쓰는 것이 이 사이트에서 있을 법한
    일이고, 그때 한 집이 한 브라우저다. 승인제가 이미 문지기라 여기서 막는 것은
    "표가 스팸으로 차오르는 것"뿐이다.
  - **못 읽으면 제한하지 않는다.** 읽기 실패로 댓글 쓰기를 막으면 Supabase 가
    잠깐 흔들릴 때 아무도 못 쓴다 — 막아서 얻는 것보다 잃는 것이 크다.
- **2026-09-13 — 덫 칸을 거절하되 성공한 척하지 않는다.** 흔한 방식은 조용히
  성공을 돌려주는 것인데, **진짜 사람이 자동 완성 때문에 걸릴 수 있다.** 그때
  "보냈습니다"만 뜨면 영영 이유를 모른다.
- **2026-09-13 — 공유 주소를 `window.location` 에서 읽지 않는다.** 서버가 준
  `origin` 과 `path` 로 조립한다. 주소창을 읽으면 **지금 보고 있는 사람에게 붙은
  utm 이 그대로 따라 나간다** — 카카오톡으로 받은 링크를 열어 다시 공유하면
  `utm_source=kakao` 가 남아, 그 방문은 영원히 카카오에서 온 것으로 센다.
  미리보기 도메인에서 공유했을 때 미리보기 주소가 나가는 것도 같은 사고다.
- **2026-09-13 — 링크 복사와 시스템 공유에도 utm 을 붙인다.** 이 둘은 나가는 곳을
  알 수 없다(카카오톡 대화창일 수도, 메모장일 수도 있다). 그래도 `direct` 로
  흘려보내는 것보다 낫다고 봤다 — **`direct` 로 섞이면 그 방문이 공유에서 왔다는
  사실 자체가 사라진다.** 다섯 수단이 `utm_medium=social` 로 소셜 한 칸에 모이고
  `utm_source` 로 갈리므로, 표에서 따로 읽어 낼 수 있다.
- **2026-09-13 — 카카오톡만 남의 스크립트를 부른다.** 카카오톡으로 보내는 공개된
  주소 규약이 없어서 JS SDK 를 실어야 한다(X·페이스북은 주소만 열면 되고, 링크
  복사·시스템 공유는 브라우저가 해 준다). 그래서 **키가 없으면 그 버튼만 없고
  스크립트도 안 싣는다** — 키 없이 실어 놓으면 아무 값도 못 하는 외부 스크립트가
  모든 방문자에게 내려간다.
  - `integrity` 를 달지 않았다. 이 버전의 해시를 저장소에서 확인할 방법이 없고,
    **틀린 해시를 적으면 버튼이 조용히 죽는다.** 확인하지 않은 값을 적어 두는
    것보다 안 적는 편이 정직하다. 버전은 고정했다(`2.7.6`).
- **2026-09-13 — 댓글만 `Suspense` 뒤에 뒀다.** 댓글은 DB 를 한 번 읽어야 나오고,
  그동안 미리보기와 글이 기다릴 이유가 없다. 만들러 온 사람에게 저장소 응답 시간을
  물릴 일이 아니다.

    컴포넌트가 트리에 들어가 렌더가 통째로 막혔고, 게임·글 페이지 테스트 셋이
    한꺼번에 깨졌다. 테스트가 맞았다 — 본문이 댓글을 기다리고 있었다는 뜻이다.
- **2026-09-13 — 공유 줄은 제목이 아니라 이름 붙은 묶음이다.** 처음엔 `h3` 로
