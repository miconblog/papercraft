# 이슈 관리 규칙

이슈 1건 = 파일 1개. 전체 현황은 [BOARD.md](BOARD.md)에서 본다.

## 파일 이름

```
IDE-<번호>-<영문-슬러그>.md
예) IDE-001-first-thing-to-do.md
```

번호는 재사용하지 않는다. 취소된 이슈도 번호를 비워두고 `cancelled`로 남긴다.

## 번호 대역

마일스톤이 정해지면 대역을 여기에 적는다(예: `001–009` = M0). 정해지기 전에는
`001`부터 차례로 쓴다.

| 대역    | 마일스톤                               |
| ------- | -------------------------------------- |
| 001–003 | M0 — 기반 (저장소·인쇄 검증·도안 규격) |
| 004–010 | M1 — 첫 릴리스: 축구 게임판            |
| 011–020 | M2 — 게임 확장                         |

대역이 찼는데 그 마일스톤에 이슈가 더 필요하면 **다음 빈 번호를 쓰고 마일스톤
칸으로 구분한다** — `IDE-012`(M1)가 그렇다. 번호를 재사용하지 않는 것이 대역을
지키는 것보다 중요하다.

## 선행 · 후행 적는 법

**번호는 백틱으로 적는다.** 여러 개면 `·`로 잇는다:

```
| 선행 | `IDE-002` · `IDE-005` |
| 후행 | `IDE-011` |
```

마크다운 링크(`[IDE-002](IDE-002-….md)`)도 번호로 읽는다 — 단 **링크 글자가 번호
그 자체일 때만**이다. `[먼저 이것부터](IDE-002-….md)`처럼 제목을 적으면 번호로 안 읽혀
**조용히 없는 이슈를 가리키게** 된다. 관계는 틀려도 아무것도 안 깨지는 데이터라
이런 실수는 알아서 드러나지 않는다.

**관계는 양쪽에 적는다.** A의 `후행`에 B를 적었으면 B의 `선행`에도 A가 있어야 한다.
한쪽만 적으면 이슈 창이 *깨진 관계*로 센다 — 창 헤더의 주황 숫자가 그것이고,
눌러서 목록을 펼치면 어느 칸이 비었는지 말해 준다.

**풀린 선행은 지우지 말고 취소선**(`~~IDE-002~~`)으로 남긴다. 무엇을 기다렸는지가
기록으로 남고, 앱은 취소선을 "이제 안 막는다"로 읽는다.

## 상태

| 값          | 뜻                                       |
| ----------- | ---------------------------------------- |
| `todo`      | 착수 전                                  |
| `doing`     | 진행 중 — **동시에 3개를 넘기지 않는다** |
| `blocked`   | 선행 이슈나 외부 답변 대기               |
| `review`    | 구현 완료, 검증 중                       |
| `done`      | 수용 기준 전부 충족                      |
| `cancelled` | 하지 않기로 결정. 이유를 남긴다          |

## 영역

프로젝트에 맞게 고친다. 예) `research` · `backend` · `frontend` · `app` · `infra` · `content` · `biz`

## 우선순위

| 값  | 뜻                            |
| --- | ----------------------------- |
| P0  | 이게 막히면 다른 일을 못 한다 |
| P1  | 출시에 필요하다               |
| P2  | 출시 후에 해도 된다           |

## 추천 모델 · Effort

이 이슈를 코딩 에이전트로 작업할 때 어떤 모델·강도가 맞는지 적어둔다. 되돌리기
비싸거나(스키마·인쇄 정확도 같은 근간 결정) 이후 이슈가 여기 의존하면 상위 모델·
높은 effort를, 명세가 이미 명확한 구현 작업이면 하위 모델·낮은 effort를 쓴다.

| 값     | 뜻                                                                                                                                            |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 모델   | Sonnet 5 · Opus 5 · Fable 5.1                                                                                                                 |
| Effort | low · medium · high · xhigh · max — Claude Code 기본값은 이미 `xhigh`라, 대부분의 이슈는 여기서 **내려서** 쓰고 근간 이슈만 기본값을 유지한다 |

## 이슈 템플릿

```markdown
# IDE-XXX · 제목

| 항목        | 값       |
| ----------- | -------- |
| 상태        | `todo`   |
| 영역        | backend  |
| 우선순위    | P1       |
| 마일스톤    | M0       |
| 추정        | 3d       |
| 추천 모델   | Sonnet 5 |
| 추천 Effort | medium   |
| 선행        | —        |
| 후행        | —        |

## 배경

왜 필요한가. 어떤 문서·결정에서 나왔는가.

## 할 일

- [ ] 항목

## 수용 기준

- [ ] 무엇이 충족되면 done인가. 검증 가능한 문장으로 쓴다.

## 결정 기록

작업하며 남긴다. 날짜와 함께.
```

## 운영 규칙

1. **상태를 바꾸면 BOARD.md도 같이 고친다.** 보드가 진실의 원본이다.
2. **작업을 마치면 체크박스를 그 자리에서 갱신한다.** 결정 기록만 쓰고 체크박스를 두면
   나중에 무엇이 남았는지 알 수 없다.
   - 완료 항목에는 **결론을 한 줄로** 남긴다 — 이슈만 봐도 무엇을 확인했는지 보이게
   - 부분적으로만 확인한 것은 `⚠︎`로 표시하고 무엇이 빠졌는지 적는다
   - 불필요해져서 안 한 항목은 `~~취소선~~` + 이유를 쓰고 완료로 표시한다
   - **다른 이슈로 넘긴 것은 체크하지 않는다.** 이관처를 적고 미완으로 둔다
3. **범위가 바뀌면 수용 기준부터 고친다.** 취소된 기능이 수용 기준에 남아 있으면
   영원히 충족되지 않아 이슈가 닫히지 않는다.
4. `research` 이슈는 **결론을 결정 기록에 남기고 done** 처리한다. 결론이 없으면 done이 아니다.
5. 이슈가 하루 만에 안 끝날 것 같으면 쪼갠다.
6. 새 이슈는 번호 대역 안에서 다음 번호를 쓴다. BOARD에 백로그로만 있던 항목을 착수할 때 파일을 만든다.
7. **`선행`·`후행`은 양쪽에 적는다**(위 "선행 · 후행 적는 법"). 이슈 창의 "새 이슈"에서
   `+`로 번호를 고르면 표기 실수가 안 난다.

### 진행 점검

```bash
# 상태와 체크박스가 어긋난 이슈 찾기
for f in issues/IDE-*.md; do
  d=$(grep -cE '^- \[x\]' "$f"); t=$(grep -cE '^- \[ \]' "$f")
  echo "$(basename "$f") 완료 $d / 미완 $t"
done
```

`done` 인데 미완이 남아 있거나, `doing` 인데 완료가 0이면 둘 중 하나가 틀린 것이다.
