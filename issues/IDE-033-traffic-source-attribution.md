## 배경

사용자 요청(2026-09-17) — "방문 통계를 좀더 상세하게 알고 싶어. 예를들면 utm
파라메터 분석을 통해서 어느채널에서 왔는지 제대로 알고 싶어."

`IDE-013` 부터 `utm_source/medium/campaign` 과 referrer 호스트는 **저장해 왔다.**
대시보드가 다섯 갈래 합계만 보여 줬을 뿐이다. 그런데 운영 원본(112줄)을 열어 보니
그 합계부터 틀려 있었다.

| 무엇이 틀렸나      | 원본에서 본 것                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------- |
| 세션이 쪼개진다    | 페이스북 utm 으로 들어와 일곱 화면을 본 세션이 소셜 1 · 직접 6. 채널이 둘 이상인 세션이 3개 |
| 카페가 검색이 된다 | `utm_source=naver_cafe&utm_medium=community` 다섯 줄이 전부 `organic` — `naver.` 에 걸렸다  |
| 소스 표가 없다     | 페이스북과 네이버 카페가 같은 "소셜" 한 칸에 섞여 갈라 볼 수 없다                           |
| 인앱이 사라진다    | referrer 도 브라우저 이름도 없는 iOS 줄 — 카카오톡·네이버 같은 앱 안에서 연 흔적이다        |

## 결정 기록

- **2026-09-17 — last non-direct click.** 출처 없는 줄만 물려받고, 새 utm·외부
  referrer 는 스스로 출처가 된다. 세션 첫 줄로 고정(first touch)하면 세션 도중 다른
  링크로 다시 들어온 것이 사라진다.
- **2026-09-17 — 물려주기는 SQL 이 한다.** `IDE-025` 와 같은 이유 — 세션을 찾는
  자리가 이미 거기고, 직전 줄 하나만 보면 된다(직전 줄도 같은 규칙을 거쳤다).
- **2026-09-17 — 네이버·다음 앱은 소셜로 치지 않는다.** 그 안에서는 검색인지
  카페인지 모른다. 채널은 직접 방문으로 두되 소스 표에 앱 이름이 남는다.
- **2026-09-17 — `utm_content`·`utm_term` 은 집계 키에 안 넣는다.** 줄 수가
  캠페인마다 곱으로 는다. 원본에는 있으니 필요하면 SQL 로 본다.
- **2026-09-17 — 소급한다.** `IDE-025` 는 표본이 며칠치라 소급하지 않았지만,
  이번엔 실제 유입(페이스북·네이버 카페)이 섞여 있고 틀린 칸이 눈에 띄게 크다.

### 2026-09-17 · 운영 DB 적용

`010` 한 건. 적용 전 검색 5 · 소셜 5 · 쪼개진 세션 3 → 적용 뒤 위 수용 기준의
숫자다. `daily_source` 는 RLS 가 켜져 있고 서비스 롤만 읽으며, PostgREST 로
`daily_source` · `daily_channel.downloads` 를 읽는 길까지 확인했다.

함수 ACL 에 PUBLIC 실행(`=X`)이 있는데 **이번에 생긴 것이 아니다** — 001 부터 네
함수 모두 Postgres 기본값 그대로다. anon·authenticated 는 스키마 사용 권한이 없어
닿지 못한다. 적용기가 `public` 낱말을 막아 마이그레이션으로는 회수할 수 없으므로
그대로 둔다.
