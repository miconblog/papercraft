## 배경

지금 이 사이트는 **누가 오는지, 무엇을 뽑아 가는지 하나도 모른다.** `IDE-011`이
"게임 2종 추가"를 들고 있고 보드의 후보 목록(URL 공유·보관함·인쇄소 주문)도
전부 "요구가 확인되지 않았다"로 미뤄져 있는데, 확인할 수단이 없다. 어떤 게임을
더 만들지, 공유가 정말 필요한지는 **조회수와 PDF 다운로드수**가 답한다.

외부 분석 도구(GA 등)를 붙이지 않고 자체 구현하는 이유는 두 가지다 — 아이와
함께 쓰는 사이트라 **제3자에게 방문 기록을 넘기지 않는 편이 낫고**, 필요한 지표가
"게임별 조회수·다운로드수"로 좁아 범용 도구가 과하다.

저장소는 Supabase(Postgres)를 쓰는데, **이 프로젝트는 다른 서비스가 이미 쓰고
있다.** 그래서 `public`이 아니라 **`daddys_craft`** 스키마 하나만 쓰고, 남의
스키마와 마이그레이션 이력에는 손대지 않는다. 이 제약이 아래 설계를 거의
전부 결정한다.

## 할 일

### 스키마

- [x] `db/migrations/NNN-*.sql` — 번호 붙은 평범한 SQL 파일. Supabase CLI 를 쓰지 않는다
      → `001-analytics.sql`(스키마·표·함수) · `002-daily-maintenance-schedule.sql`(정리 일감)
- [x] `npm run db:migrate` — `psql`로 순서대로 적용하고 `daddys_craft.migrations`에
      적용 이력을 남긴다 (남의 `supabase_migrations` 를 건드리지 않는다)
      → `scripts/db-migrate.mts`. 한 파일 = 한 트랜잭션, 적용 뒤 파일이 바뀌면 경고한다
- [x] 모든 DDL 을 재실행 가능하게 (`create ... if not exists`)
      → 이력을 비우고 통째로 재적용해 확인했다 — `NOTICE ... skipping` 만 나오고 오류 없음
- [x] 마이그레이션이 `daddys_craft` 밖을 건드리지 않는지 검사 —
      `public` · `auth` · `storage` 를 언급하면 적용을 거부한다
      → 낱말 경계로 본다(`authenticated` 롤은 `auth` 에 안 걸린다). 하나라도 걸리면 한 줄도 적용하지 않는다
- [x] `create schema if not exists daddys_craft`
      → 적용 확인. 이 프로젝트엔 `lylo_app` · `rlibro_*` 등 남의 스키마가 실제로 있다
- [x] `events` 테이블 — 원본 이벤트 한 줄 = 방문/행동 하나
      (`id` · `occurred_at` · `type` · `session_id` · `visitor_id` · `path` ·
      `game_id` · `referrer` · `utm_*` · `channel` · `user_agent` 요약 · `country`)
      → `referrer` 는 **호스트만**, UA 는 `ua_browser`·`ua_os`·`ua_device` 세 칸으로 줄여 넣는다
- [x] RLS 켜고 **어떤 정책도 만들지 않는다** — 스키마가 API 에 노출되므로 이것이
      익명 키를 막는 유일한 장치다. 정책을 하나 만드는 순간 그만큼 열린다
      → 5개 표 전부 `relrowsecurity = t`, `pg_policies` 개수 0
- [x] `revoke all on schema daddys_craft from anon, authenticated` — 이중으로 잠근다
      → 표·함수·시퀀스까지 회수. `has_schema_privilege('anon','daddys_craft','USAGE')` = false
- [x] 집계 뷰 — 일자별 PV/UV, 채널별 유입, 게임별 조회·다운로드
      → **뷰가 아니라 표로 만들었다**(`daily_traffic`·`daily_channel`·`daily_game`).
      뷰는 원본을 지우는 순간 같이 비어 "365일 뒤에도 집계는 남는다"를 못 지킨다
- [x] 원본 이벤트 365일 후 정리 (pg_cron 일 1회) — 일자별 집계는 영구 보관
      → 2026-09-07 사용자가 pg_cron 을 켜서 일감까지 걸었다. 매일 15:10 UTC(= KST 자정
      10분 뒤) `run_daily_maintenance()` — `postgres` 롤, `active = t`.
      오래된 것과 최근 것을 섞어 심고 그 명령을 그대로 불러, 오래된 원본만 지워지고
      집계는 남는 것을 확인했다

### 수집

- [x] `supabase-js` 클라이언트를 서버 전용 모듈 한 곳에서만 만든다
      (`createClient(url, serviceRoleKey, { db: { schema: 'daddys_craft' } })`)
      → `src/lib/analytics/client.ts`. 스키마 이름은 `config.ts` 의 상수다
- [x] 그 모듈에 `import 'server-only'` — 서비스 롤 키가 클라이언트로 새는 것을
      빌드 단계에서 막는다
      → 빌드 뒤 `.next/static` 에서 서비스 롤 키·DB 접속 문자열·salt·비밀번호를 찾아 0건 확인
- [x] 대시보드 _Exposed schemas_ 에 `daddys_craft` 추가 (선행 설정, 문서에 남긴다)
      → `docs/analytics.md` §"처음 한 번만 하는 설정" · `.env.example` 머리말.
      빠졌을 때 나는 로그(`Invalid schema: daddys_craft`)까지 적어 뒀다
- [x] `POST /api/analytics/event` — 서버에서 받아 `daddys_craft.events` 에 넣는다
      → 몸통은 `url`·`referrer` 둘뿐. 방문자·채널·국가는 서버가 헤더에서 만든다.
      언제나 204 를 낸다 — 브라우저는 결과로 할 일이 없다
- [x] 페이지뷰 수집 — App Router 클라이언트 네비게이션까지 포함
      → `PageViews.tsx` 가 `usePathname()` 을 본다. `useSearchParams()` 는 안 쓴다 —
      루트 레이아웃에서 그걸 읽으면 사이트 전체가 정적 렌더링에서 빠진다(빌드로 확인)
- [x] 방문자 식별 — 쿠키 없이 `visitor_id = hash(그날의 salt + IP + UA + 도메인)`
      (IP·UA 원본은 저장하지 않는다. salt는 자정에 버린다)
      → salt 를 키로 쓰는 HMAC 이다. 날짜 경계는 KST — 집계 표의 `day` 와 같은 경계라야
      하루 UV 가 이틀에 걸쳐 쪼개지지 않는다
- [x] `session_id` — 30분 무활동이면 새 세션. 세션 수·세션당 페이지 수를 낸다
      → 세션 이어붙이기를 `record_event` 안(SQL)에서 한다. 앱에서 "조회 → 삽입" 두 번으로
      나누면 동시에 들어온 두 요청이 각자 새 세션을 만든다. 실 DB 로 확인
- [x] 채널 분류 — `utm_source`/`utm_medium` 우선, 없으면 `referrer`로
      direct · organic · social · referral 판정
      → **`campaign` 을 하나 더 뒀다.** 뉴스레터·QR 처럼 넷 중 어디도 아닌 utm 유입을
      `referral` 에 밀어 넣으면 표가 거짓말을 한다. 광고(`utm_medium=cpc`)도 여기로 보낸다 —
      `utm_source=google` 만 보고 organic 이라 적으면 돈 주고 산 방문이 자연 유입으로 둔갑한다
- [x] 게임별 조회 — `/games/[id]`, `/games/[id]/edit`, `/games/[id]/print`
      → 세 경로 모두 확인. **등록소에 있는 id 만 인정한다** — 경로는 누구나 지어내 부른다
- [x] PDF 다운로드 — `/api/games/[id]/export`에서 **서버가 직접** 기록한다
      (클라이언트 이벤트는 차단기·이탈로 빠진다)
      → `after()` 로 응답 바이트가 다 나간 뒤에 돈다
- [x] 봇·프리렌더 요청 제외
      → UA 로 거른다. UA 가 없는 요청도 사람으로 치지 않는다
- [x] 수집 실패가 페이지나 PDF 응답을 절대 깨뜨리지 않게 한다 (fire-and-forget)
      → 실제로 한 건 잡았다: **`after()` 는 요청 스코프 밖에서 불리면 던진다.** 그대로 두면
      분석 하나 때문에 PDF 가 500 이 된다 — `afterResponse()` 로 감쌌다.
      `Invalid schema` 로 막힌 동안에도 페이지 200 · 수집 204 로 멀쩡히 돌았다

## 수용 기준

- [x] 페이지를 열면 `daddys_craft.events`에 이벤트가 한 줄 쌓인다
      → 개발 서버 + 실 DB 로 확인
- [x] 같은 방문자가 하루 안에 여러 페이지를 봐도 그날 UV는 1로 센다
      → 방문자 A 가 3페이지, B 가 1페이지 → PV 4 · UV 2 · 세션 2
- [x] 날짜가 바뀌면 같은 방문자라도 새 `visitor_id`가 나온다(salt가 바뀌므로)
- [x] utm 파라미터가 붙은 링크와 안 붙은 링크가 서로 다른 채널로 분류된다
      → 같은 `/` 방문이 `organic`(검색 유입) · `campaign`(utm) 으로 갈렸다
- [x] 게임 상세를 열면 그 게임의 조회수가, PDF를 받으면 다운로드수가 오른다
      → `daily_game`: soccer 조회 2 · 다운로드 1
- [x] PDF 다운로드수는 **브라우저에서 이벤트가 안 와도** 기록된다
      → JS 를 돌리지 않는 `curl` 로 내보내기 API 를 직접 쳐서 확인
- [x] 클라이언트 번들에 서비스 롤 키·DB 접속 문자열이 들어 있지 않다
      → 빌드 뒤 `.env.local` 의 다섯 값을 `.next/static` 전체에서 찾아 전부 0건
- [x] 익명 키로 `daddys_craft.events` 를 읽거나 쓰면 거부된다
      → `set role anon` · `set role authenticated` 로 읽기·쓰기·함수 실행 전부
      `permission denied for schema`. PostgREST 가 익명 키 요청에 갈아입는 바로 그 롤이다
- [x] 마이그레이션을 두 번 돌려도 결과가 같고 오류가 나지 않는다
      → 이력을 비우고 통째로 재적용하기를 세 번. `NOTICE ... skipping` 만 나온다
- [x] 마이그레이션·런타임 어느 것도 `daddys_craft` 밖의 객체를 만들거나 고치지 않는다
      → 우리 객체 13개 전부 `daddys_craft` 안. 밖으로 나간 것은 `cron.job` 의
      **우리 이름의 줄 하나**뿐이다(객체가 아니라 행이고, 남의 일감은 건드리지 않는다).
      확장을 켜는 것은 마이그레이션이 하지 않는다 — 사용자가 직접 켰다
- [x] `public` 스키마의 기존 테이블 목록이 작업 전후로 동일하다
      → 작업 전 스냅샷과 `diff` 결과 무차이
- [x] 개인을 특정할 수 있는 값(IP 원본·전체 UA)이 저장되지 않는다
      → 실제로 쌓인 줄에 IP 도 UA 원본도 없다. referrer 는 호스트만(`www.google.com`),
      검색어가 든 전체 URL 은 버린다
- [x] Supabase 환경변수가 없어도 사이트와 테스트가 그대로 동작한다
      → `env -i` 로 테스트 387건 통과, `.env.local` 을 치우고 빌드 성공
- [x] Supabase가 죽어 있어도 페이지 로드와 PDF 내보내기가 실패하지 않는다
      → 검증 도중 실제로 겪었다. _Exposed schemas_ 설정 전까지 모든 기록이
      `Invalid schema` 로 실패했는데, 페이지는 200 · 수집은 204 · PDF 는 143KB 로
      멀쩡히 나왔다. 서버 로그에 경고만 남는다
- [x] `/admin/analytics`가 비밀번호 없이는 열리지 않는다
      → 쿠키 없이·위조 쿠키로 307 → `/admin/login`. 유효 쿠키로만 200
- [x] 365일 지난 원본 이벤트가 지워져도 일자별 집계 수치는 그대로다
      → 2025-01-02 이벤트 3건을 심고 `purge_events(365)` → 원본 0건,
      `daily_traffic`·`daily_game` 수치는 그대로. 지운 날을 다시 집계해도 0 으로 덮이지 않는다

## 결정 기록

- 2026-09-07 · 스키마를 `daddys_craft`로 둔다(사용자 지정). PostgREST로 이 스키마를
  쓰려면 Supabase 대시보드의 **Exposed schemas**에 추가해야 하는데, 그러면 잠금이
  느슨해진다 — **서버에서 서비스 롤로만 쓰고 스키마는 노출하지 않는 쪽**을 기본으로 잡는다.
- 2026-09-07 · **관리자 인증은 환경변수 비밀번호 한 개**(사용자 결정 — 관리자가
  1명뿐이다). Supabase Auth를 붙이면 사용자 테이블·세션·비밀번호 재설정까지
  딸려 오는데, 쓸 사람이 한 명이면 전부 짐이다. 대신 두 가지는 지킨다 —
  비교를 `timingSafeEqual`로 하고(문자열 `===`는 몇 글자까지 맞았는지가
  응답 시간에 새어 나온다), 비밀번호가 설정돼 있지 않으면 401이 아니라
  **404**를 낸다(경로의 존재 자체를 숨긴다).
- 2026-09-07 · **원본 이벤트 365일, 일자별 집계는 영구.** 원본이 있어야 나중에
  생긴 질문("축구를 본 사람 중 몇 %가 PDF를 받았나")에 답할 수 있지만, 한 줄
  300바이트로 하루 1,000 PV여도 월 10MB 안팎이라 Supabase 무료 티어(500MB)에
  1년은 넉넉하다. 1년이면 방학·학기 같은 계절성까지 보인다. 지운 뒤에도 추이는
  집계에 남는다.
- 2026-09-07 · **UV는 "일간 순방문자"로 정의한다** — 쿠키를 심지 않고
  `hash(그날의 salt + IP + UA + 도메인)`으로 식별하고 salt를 자정에 버린다
  (Plausible·Fathom과 같은 방식). 영구 쿠키를 쓰면 몇 달 뒤 재방문까지 같은
  사람으로 묶을 수 있지만 동의 배너가 필요해지고, 아이와 함께 쓰는 사이트에
  제3자 추적과 같은 장치를 두는 셈이 된다.
  - **대가를 분명히 적어 둔다 — 주간·월간 UV는 정확하지 않다.** 같은 사람이
    사흘 오면 3명으로 센다. 화면에도 "일간 UV"라고 쓰고, 주간·월간은 대략치로만
    읽는다. 나중에 정확한 재방문율이 필요해지면 그때 동의 배너와 함께 재검토한다.
  - `session_id`(30분 무활동이면 새로)를 함께 남긴다. 세션 수·세션당 페이지 수는
    UV와 다른 것을 말해 주고, 스키마에 칸이 이미 있어 추가 비용이 없다.
- 2026-09-07 · **익명 키를 쓰지 않는다**(사용자 결정 — 모든 접근을 백엔드 API로).
  Supabase 클라이언트는 서버에서 서비스 롤로만 만들고, URL도 `NEXT_PUBLIC_`을
  떼 번들에 나가지 않게 한다. 그래서 `events`의 RLS는 **정책을 하나도 만들지
  않는다** — RLS를 켜고 정책이 없으면 서비스 롤 외에는 전부 막힌다. "insert만
  허용" 같은 정책을 두면 그 구멍으로 누구나 가짜 이벤트를 밀어 넣을 수 있다.
- 2026-09-07 · **Supabase CLI 를 쓰지 않는다**(사용자가 짚었다 — 프로젝트를 다른
  서비스와 공유한다). `supabase db reset` 은 **남의 데이터를 통째로 날리고**,
  `supabase db push` 는 이력의 주인이 다른 저장소인 `supabase_migrations` 테이블을
  두 저장소가 다투게 만든다. 대신 번호 붙은 평범한 `.sql` 파일을 `psql` 로 적용하고,
  적용 이력은 **우리 스키마 안**(`daddys_craft.migrations`)에 남긴다.
  - 마이그레이션 스크립트가 `public` · `auth` · `storage` 를 언급하는 SQL 을
    거부하게 한다. 공유 DB 에서 실수 한 번의 대가가 우리 쪽에만 그치지 않는다.
- 2026-09-07 · **`supabase-js` 대신 Postgres 직접 연결.** 앞선 결정("스키마를
  노출하지 않고 서비스 롤로 쓴다")은 **성립하지 않는다** — `supabase-js` 는
  PostgREST 를 거치고, PostgREST 는 _Exposed schemas_ 에 있는 스키마만 본다.
  서비스 롤 키는 RLS 를 우회할 뿐 이 목록은 우회하지 못한다. 노출하려면 공유
  프로젝트의 API 설정을 바꿔야 하는데, 그건 우리 것이 아니다.
  - 직접 연결이면 이 문제가 통째로 사라진다. 서비스 롤 키도, `SUPABASE_URL` 도
    필요 없고 **접속 문자열 하나**로 끝난다.
  - 대신 **서버리스에서 커넥션 관리가 우리 책임**이 된다. 트랜잭션 풀러(6543)를
    쓰고 prepared statement 를 끈다. 직접 연결(5432)을 쓰면 함수 인스턴스마다
    커넥션을 열어 **같은 DB 를 쓰는 다른 서비스까지 막는다** — 공유 프로젝트에서
    가장 현실적인 사고 시나리오다.
  - DDL 은 세션 풀러(5432)로 돌린다(`SUPABASE_DB_MIGRATION_URL`). 이 값은 로컬·CI
    에만 두고 배포 환경에는 넣지 않는다.
- 2026-09-07 · **`supabase-js` 로 되돌린다**(사용자 결정 — 지금 필요한 것은 단순
  읽기·쓰기뿐이다). 직접 연결은 서버리스 커넥션 관리를 우리 책임으로 만드는데,
  이벤트 한 줄 넣자고 치르기엔 비싼 값이다. `SUPABASE_DB_URL` 은 남겨 두되
  **마이그레이션 적용에만 쓰고**, 나중에 여러 문장을 한 트랜잭션으로 묶어야 할
  일이 생기면 그때 런타임에서도 쓴다.
  - **선행 설정이 하나 붙는다** — 대시보드 _Exposed schemas_ 에 `daddys_craft` 를
    추가해야 한다. PostgREST 서버 설정이라 서비스 롤 키로 우회되지 않는다.
    기존 목록에 더하기만 하므로 다른 서비스에는 영향이 없다.
  - 노출되는 만큼 **RLS 가 실제 방어선이 된다.** 정책을 하나도 만들지 않고,
    `anon` · `authenticated` 롤에서 스키마 권한 자체를 회수해 이중으로 잠근다.
    앞선 설계에서 RLS 는 "어차피 안 닿으니 보험"이었지만 이제는 본선이다.
  - 클라이언트를 만드는 모듈에 `import 'server-only'` 를 건다. 서비스 롤 키는
    한 번 클라이언트 번들에 들어가면 **DB 전체가 열린다** — 런타임에 발견하기엔
    늦으므로 빌드가 깨지게 한다.
  - 스키마 이름은 상수로 박는다(환경변수로 두지 않는다). 배포마다 달라질 값이
    아니고, 오타가 나면 조용히 다른 스키마에 쓰게 된다.

### 구현하며 (2026-09-07)

- **`service_role` 은 새 스키마에 아무 권한이 없다.** _Exposed schemas_ 를 넣어도
  그대로면 `permission denied for schema daddys_craft` 로 막힌다 — 이 잠금 설계에서
  가장 놓치기 쉬운 자리였다(RLS·revoke 만 신경 쓰다 grant 를 빼먹는다).
  - 여는 김에 **표에 직접 쓰는 권한은 주지 않았다.** 이벤트는 `record_event`
    (security definer) 로만 들어가고, 원본 `events` 는 **서버조차 직접 읽지 못한다.**
    서비스 롤 키가 새어 나가도 할 수 있는 일이 "이벤트를 한 줄 넣는 것"에 그친다.
  - 반대로 `purge_events` · `run_daily_maintenance` 는 **일부러** security definer 가
    아니다. Postgres 는 새 함수의 실행 권한을 누구에게나 열어 두는데, 거기에 정의자
    권한까지 얹으면 키가 새면 원본을 통째로 지울 수 있다. 호출자 권한이면 표에
    delete 권한이 있는 소유자만 실제로 지운다 — `set role service_role` 로 불러
    `permission denied` 를 확인했다.
- **집계를 뷰가 아니라 표로 만들었다.** 뷰였다면 "365일 뒤 원본을 지워도 집계는
  남는다"가 성립하지 않는다 — 지우는 순간 1년 전 그래프가 통째로 0 이 된다.
  `purge_events()` 는 지우기 전에 지울 구간을 반드시 한 번 더 집계하고,
  `rollup_daily()` 는 원본이 이미 없는 날에는 손대지 않는다.
- **`after()` 는 요청 스코프 밖에서 불리면 던진다.** 내보내기 라우트에서 그대로
  쓰면 분석 하나 때문에 PDF 가 500 이 된다 — "수집 실패가 응답을 절대 깨뜨리지
  않는다"가 정확히 거기서 무너진다. `afterResponse()` 로 감쌌다.
- **`host` 헤더에는 포트가 있고 referrer 의 hostname 에는 없다.** 그대로 견주다
  실 요청에서 사이트 안 이동이 `referral` 로 잡히는 걸 봤다. 포트를 떼고 비교한다.
- **채널에 `campaign` 을 하나 더 뒀다.** 이슈에 적힌 네 갈래로는 뉴스레터·QR 같은
  utm 유입을 `referral` 에 밀어 넣게 되는데, 그러면 표가 거짓말을 한다.
  광고(`utm_medium=cpc`)도 여기로 보낸다 — `utm_source=google` 만 보고 organic 이라
  적으면 **돈 주고 산 방문이 자연 유입으로 둔갑한다.**
- **Next 16 에서 미들웨어는 `proxy` 다**(`middleware.ts` 는 deprecated, 기본
  Node.js 런타임). 다만 문서가 "proxy 는 CDN 으로 나갈 수 있으니 그것만 믿지 말라"고
  못박아서, `/admin/analytics` 페이지도 스스로 한 번 더 확인한다. matcher 를 잘못
  건드리면 그 검사가 **조용히** 사라지는데, 그때 통계가 열리면 아무도 눈치채지 못한다.
- **`useSearchParams()` 를 쓰지 않았다.** 루트 레이아웃에서 읽으면 사이트 전체가
  정적 렌더링에서 빠진다. utm 은 이펙트 안에서 `window.location.search` 로 읽으면
  되고, 빌드 결과로 `/` 와 `/games/soccer` 가 그대로 정적인 것을 확인했다.
- **`import 'server-only'` 때문에 기존 테스트가 깨졌다.** jsdom 환경은 클라이언트로
  잡혀 서버 모듈을 하나도 못 불러온다. `vitest.config.mts` 에서 빈 모듈로 돌렸다 —
  진짜 방어선은 `next build` 라 이 우회로 방어가 약해지지 않는다.
- **pg_cron 은 마이그레이션이 켜지 않는다.** 확장을 켜는 것은 공유 프로젝트 전체에
  걸리는 변경이고, 수용 기준("`daddys_craft` 밖의 객체를 만들지 않는다")과 정면으로
  부딪힌다. `002` 는 확장이 **있을 때만** 일감을 걸고 없으면 알림만 남긴다.
  - 2026-09-07 사용자가 켰고, 일감을 걸어 끝까지 확인했다.
  - 그러면서 **내가 문서에 적어 둔 안내가 틀린 것이 드러났다** — "켠 뒤
    `npm run db:migrate` 를 다시 돌리면 걸린다"고 썼는데, 이미 이력에 있는 파일은
    러너가 건너뛴다. 바깥 상태에 따라 하는 일이 달라지는 파일은 이 부류가 더 나올
    것이라 `--redo <파일명>` 을 붙였다. 이력 표에서 줄을 손으로 지우라고 안내하는
    것보다 낫다 — 공유 DB 에서 `delete` 를 손으로 치게 만드는 안내는 언젠가
    `where` 절을 빠뜨린다.
- **선행 설정을 사용자가 적용했다** — _Exposed schemas_ 에 `daddys_craft` 가 들어간
  뒤 실 DB 로 끝까지 확인했다. 무엇을 봤고 무엇이 나왔는지는 수용 기준 줄마다 적었다.
