## 배경

사용자가 잡아냈다(2026-09-09). **새로고침할 때마다 PV 가 쌓인다.** 그러면 그
숫자로는 아무것도 판단할 수 없다 — F5 를 몇 번 눌렀느냐가 "사람들이 얼마나
봤느냐"를 덮어 버린다.

`IDE-024` 로 봇을 걸러 낸 직후에 나온 이야기다. 걸러 낼 것이 봇만은 아니었다.

## 세션당 한 번이 아니라 세션×경로당 한 번이다

사용자 표현은 "한 세션에는 PV 가 한 번만"이었지만, 그대로 하면 **PV 가 세션 수와
똑같아진다.** 카탈로그에서 상세로, 상세에서 만들기로 들어가는 **깊이가 통째로
사라지고**, 그 깊이가 이 사이트에서 가장 보고 싶은 것이다.

그래서 **세션 안에서 같은 경로만 묶는다** — 웹 분석에서 "순 페이지뷰"라 부르는
것이다.

| 한 세션 안에서                  | PV  |
| ------------------------------- | --- |
| `/` 를 세 번 새로고침           | 1   |
| `/` → `/games/soccer` → `/`     | 2   |
| `/` → `/games/soccer` → `/edit` | 3   |

## 판정을 어디서 하나

`record_event` 안에서 한다. 앱에서 하려면 두 가지가 걸린다.

1. **왕복이 하나 더 든다** — "이 세션에 이 경로가 있었나"를 물어야 한다.
2. **동시에 들어온 두 요청이 서로를 못 본다** — 둘 다 처음이라고 답한다.

세션 이어붙이기를 SQL 안에서 하기로 한 `IDE-013` 의 판단과 같은 이유이고,
마침 그 함수가 세션을 이미 찾아 놓은 자리라 조회 하나만 붙이면 된다.

## 처분은 003 과 같다

**줄은 남기고 표시만 한다**(`repeat_view`). 집계에서만 빠지므로 새로고침을 몇 번
했는지가 원본에 남고, 그 자체가 봇 신호이기도 하다.

**다운로드는 묶지 않는다.** 같은 도안을 두 번 받는 것은 새로고침과 달리 사람이 두
번 마음먹은 것이다.

## 수용 기준

- [x] 한 세션에서 같은 경로를 세 번 열어도 집계 PV 가 1 이다 — 운영 DB 에서
      `/` 세 번 · 상세 하나 · `/` 되돌아오기로 확인했다(되짚은 줄 3, 순 PV 2)
- [x] 다른 경로로 옮겨 간 것은 그대로 더해진다 — 깊이가 남는다
- [x] 다운로드는 두 번이면 2 다
- [x] 되짚은 줄도 `events` 에 남는다 — 새로고침 횟수를 볼 수 있다
- [x] 세션 수·UV 는 안 바뀐다
- [x] 실제 방문에서 숫자가 납득할 만하다 — 한 세션의 `/` 네 번이 순 PV 1 로
      묶이고 `/games/soccer` 는 따로 세어졌다. 의도한 그대로다

## 결정 기록

- **2026-09-09 — 세션 전체가 아니라 세션×경로로 묶는다.** 사용자 표현은 "한
  세션에 한 번"이었지만 그대로 하면 PV 가 세션 수와 같아져 화면 사이 이동이
  통째로 사라진다. 새로고침만 지우고 깊이는 남기는 것이 요청의 뜻에 맞는다.
- **2026-09-09 — 판정은 SQL 이 한다.** 앱이 하려면 왕복이 늘고, 동시에 들어온 두
  요청이 서로를 못 봐 둘 다 처음이라고 답한다.
- **2026-09-09 — 다운로드는 묶지 않는다.** 새로고침과 달리 두 번 마음먹은 것이다.

### 2026-09-09 · 실물 확인

배포본 한 세션(7건)에서 `/` 를 네 번 열었고 그중 **셋이 `repeat_view = t`** 로
묶였다. `/games/soccer` 는 다른 경로라 따로 세어졌다 — 새로고침만 지우고 깊이는
남긴다는 것이 실제 데이터에서 그대로 나왔다.

## 안 한 것

- **이미 쌓인 줄의 소급 표시.** `repeat_view` 가 기본값 `false` 라 004 이전에
  들어온 새로고침은 여전히 따로 세어진다. 원본으로 다시 계산할 수는 있지만,
  표본이 며칠치뿐이라 손대지 않았다.
