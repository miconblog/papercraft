# IDE-003 · 도안 데이터 모델과 템플릿 규격 정의

| 항목        | 값                                            |
| ----------- | --------------------------------------------- |
| 상태        | `done`                                        |
| 영역        | frontend                                      |
| 우선순위    | P0                                            |
| 마일스톤    | M0                                            |
| 추정        | 5d                                            |
| 추천 모델   | Opus 5                                        |
| 추천 Effort | xhigh (기본 유지)                             |
| 선행        | `IDE-001`                                     |
| 후행        | `IDE-004` · `IDE-005` · `IDE-006` · `IDE-010` |

## 배경

제품 방향은 **큐레이션 템플릿 + 사용자 커스터마이즈**로 정해졌다(2026-09-03). 즉
운영자가 만든 도안 안에 "사용자가 고칠 수 있는 자리"가 선언되어 있어야 한다. 축구
게임판이라면 선수 22명의 등번호, 양 팀 이름, 팀 색이 그 자리다.

그리고 **게임 하나가 종이 한 장이 아니다.** 축구 게임판은 핵심 게임판(운동장)과
오려 쓰는 부속(점수 기록칸, 게임 방법), 그리고 **접어서 세우는 조립물**(골대,
주사위)로 나뉜다. 사용자가 직접 만든 판에서 골대가 종이 상자였던 것이 이 구분의
근거다. 사용자는 이것들을 따로,
서로 다른 배율로 뽑을 수 있어야 한다. 모델이 이 분리를 표현하지 못하면 내보내기에서
특수 처리가 계속 생긴다.

이 규격이 흔들리면 게임을 추가할 때마다 에디터를 새로 짜게 된다. 도안이 늘어나기
전에 못을 박아둔다.

## 할 일

- [x] 게임 메타데이터 스키마 정의 — id, 제목, 소개, 인원, 준비물, 썸네일 — `gameDefinition`에 id·title·tagline·description·players{min,max}·supplies·thumbnail을 두고, 썸네일은 `/games/<게임 id>/` 아래만 허용
- [x] **파트 구조 정의** — 게임 = 보드 파트 1개 + 부속 파트 N개. 파트별 역할, 기준 크기(mm), 기본 배율 — 보드 1개는 검증으로 강제. 파트마다 `widthMm`·`heightMm`·`defaultScale`·`minScale`·`maxScale`·`defaultCopies`를 갖는다
- [x] 파트 종류 구분 — 보드 / 오림용 부속 / 조립물(골대·주사위 전개도) — `kind: board | cutout | buildable`
- [x] 파트별 인쇄 방향(가로·세로) 속성 정의 — 축구 게임판의 보드는 가로다 — `orientation`을 선언하고 치수와 어긋나면 검증에서 걸린다. 축구 보드는 297×210mm `landscape`
- [x] 커스터마이즈 슬롯 타입 정의 — 텍스트 · 숫자 · 색상 · 선택지와 각각의 제약 — `text`(maxLength) · `number`(min·max·integer) · `color`(#RRGGBB·palette) · `choice`(options). 기본값이 제약을 어기면 검증에서 걸리고, 입력 한 칸 검증은 `validateSlotValue`가 한다
- [x] **위치를 가진 슬롯** 정의 — 값뿐 아니라 좌표(x, y)가 사용자 편집 대상인 슬롯. 축구 게임판의 선수 22명이 그렇다 — `mode: 'marker'` 배치를 가진 슬롯이 그것이다. 이동 범위는 `regionId`가 가리키는 영역이고, 마커 배치는 슬롯당 하나뿐이다
- [x] **배치 프리셋** 정의 — 이름 + 슬롯 좌표 집합. 전술 대형(4-4-2 등)이 여기 담긴다 — `LayoutPreset`은 그룹(팀) 하나를 배치하고 `formationId`로 팀별 프리셋을 묶는다. 상대 진영용은 `mirrorPositions`로 만든다
- [x] **마커 스타일 변형** 정의 — 같은 슬롯을 원형 / 일러스트 두 가지로 렌더링할 수 있게 — `MarkerStyleSet`의 변형을 `choice` 슬롯(`selectorSlotId`)으로 고른다. 선택지와 변형 목록이 어긋나면 검증에서 걸린다
- [x] 슬롯이 어느 파트에 속하는지 표현 (등번호는 보드, 팀명은 양쪽 모두에 나올 수 있다) — `placements` 배열로 표현. 축구 팀명 슬롯이 실제로 보드(`field`)와 점수 기록칸(`score-sheet`) 양쪽에 놓인다
- [x] 도안 작성 규약 정의 — 슬롯 표시 속성, 좌표계와 단위(mm) 기준 — `docs/game-authoring.md`에 정리. 단위는 mm, 원점은 파트 좌상단, 좌표는 파트 로컬. 마커의 기준점은 중심이다
- [x] 오림선 · 접는선 · 풀칠면 표시 규약 정의 (부속·조립물 파트용) — `MARK_STYLES`에 4종(`cut`·`fold-mountain`·`fold-valley`·`glue`)의 레이어 id·굵기·파선을 고정하고, 파트 종류별 필수 표시를 검증한다
- [x] 스키마 런타임 검증 도입 — 잘못된 도안은 빌드나 로딩에서 즉시 실패하게 — `parseGame`이 등록소 모듈을 읽는 순간 돌아 예외로 터진다. 지금은 테스트가, 페이지가 등록소를 읽기 시작하면(`IDE-005`) 빌드가 그 자리에서 실패한다
- [x] 축구 게임판을 예시 인스턴스로 작성해 규격이 실제로 표현 가능한지 확인 — 파트 5개·슬롯 27개·프리셋 4개로 표현됐다. 규격을 못 바꾸고 우회한 자리는 없었다
- [x] 게임 자산 디렉터리 구조와 등록 방법 결정 — 도안은 `src/assets/games/<게임 id>/index.ts`, 정적 자산은 `public/games/<게임 id>/`, 등록은 `src/lib/games/registry.ts`에 import를 더하는 명시 방식

## 수용 기준

- [x] 스키마 타입 정의와 검증 코드가 있고 단위 테스트가 붙어 있다 — `src/lib/schema/`에 정의·검증, 테스트 57개 통과
- [x] 축구 게임판이 보드 · 부속 · 조립물 파트로 나뉘어 스키마를 통과한다 — `field`(board) · `score-sheet`·`rules-card`·`ball-markers`(cutout) · `goals`(buildable)
- [x] 파트마다 인쇄 방향이 선언되고, 방향이 치수와 어긋나면 검증에서 걸러진다 — 축구 보드는 297×210mm `landscape`. **원래 문장은 "가로 보드가 올바른 방향으로 렌더링된다"였다** — 렌더러는 `IDE-006`·`IDE-007`의 것이라 이 이슈에서 확인할 수 없어 모델이 책임지는 범위로 고쳤다(아래 결정 기록)
- [x] 파트별로 따로 출력 대상을 고를 수 있는 정보가 모델에 들어 있다 — 파트가 종류·배율 범위·기본 벌수를 각자 갖는다
- [x] 슬롯이 없거나 · 중복이거나 · 타입이 틀리거나 · 어느 파트에도 속하지 않는 도안이 검증에서 오류로 걸러진다 — 네 경우 각각에 테스트가 있다
- [x] 축구 게임판의 선수 슬롯 22개가 좌표를 갖고, 대형 프리셋이 스키마로 표현된다 — 22개 전부 마커 배치를 갖고, 4-4-2·3-5-2가 팀별 프리셋 4개로 표현됐다
- [x] 프리셋의 좌표가 필드 범위를 벗어나면 검증에서 걸러진다 — 축구 프리셋의 x를 320mm로 밀면 `영역 'playable-field' 밖이다`로 걸린다
- [x] 새 게임을 추가하는 절차가 3단계 이내로 문서에 적혀 있다 — `docs/game-authoring.md` 첫 절이 3단계다

## 결정 기록

- 2026-09-03 · 선수 배치를 사용자가 바꾸는 요구가 확정되면서 슬롯에 좌표 개념과
  배치 프리셋을 넣기로 결정. 추정을 4d에서 5d로 올렸다.
- 2026-09-03 · 사용자가 직접 만든 판 사진에서 골대가 입체 종이 상자임을 확인.
  조립물 파트 타입이 가정이 아니라 실제 요구임이 확인됐다.
- 2026-09-03 · 게임을 파트 단위로 쪼개기로 결정. 핵심 게임판과 오림용 부속을 따로
  뽑는 요구에서 나왔다. 이에 따라 추정을 3d에서 4d로 올렸다.
- 2026-09-04 · 런타임 검증 라이브러리로 **zod v4**를 채택했다. 타입 정의와 검증기가
  한 곳에 있어 둘이 어긋날 수 없고(`z.infer`로 타입을 뽑는다), 도안 안의 관계
  검사(슬롯 중복·좌표 범위·프리셋 커버리지)를 `.check()`로 같은 스키마에 붙일 수
  있다. 직접 검증기를 쓰면 의존성은 0이지만 타입과 검증이 갈라져 어긋난다.
- 2026-09-04 · 슬롯을 **kind(값의 종류) × placements(나타나는 방식)** 두 축으로
  나눴다. 처음에는 슬롯마다 좌표를 하나씩 두려 했지만, 팀명이 보드와 점수
  기록칸 양쪽에 나오는 요구를 그 모델로는 표현할 수 없었다. 배치는 배열이고
  `text`·`marker`·`paint`·`control` 네 방식이 있다. 색을 글자로 그리는 것 같은
  잘못된 조합은 검증에서 걸린다.
- 2026-09-04 · **배치 프리셋을 그룹(팀) 단위**로 두기로 했다. 22명을 한 프리셋에
  담으면 두 팀이 서로 다른 대형을 고를 수 없다. 대신 `formationId`로 같은 대형의
  팀별 프리셋을 묶어 UI가 '4-4-2' 하나로 보이게 한다. 상대 진영용은 세로 중심선
  반전(`mirrorPositions`)으로 만든다 — `IDE-010`의 "양 팀 진영에 대칭으로 적용"이
  이 방식이다.
- 2026-09-04 · **마커 스타일 선택을 `choice` 슬롯에 묶었다.** 스타일 선택을 슬롯
  바깥의 별도 축으로 두면 에디터(`IDE-006`)가 폼 자동 생성 외에 전용 UI를 하나 더
  가져야 한다. 슬롯으로 두되 선택지와 변형 목록이 정확히 일치하는지 검증해
  한쪽만 고쳐 어긋나는 일을 막는다.
- 2026-09-04 · 마커의 기준점을 **중심**으로 고정했다. `IDE-010`의 "두 세트를 바꿔
  끼워도 배치가 어긋나지 않는다"를 규격으로 보장하려는 것이다. 변형끼리 크기는
  달라도 되고, 겹침 검사에는 세트에서 가장 큰 변형을 쓴다.
- 2026-09-04 · 파트 종류는 요구대로 3종(`board`·`cutout`·`buildable`)으로 두고,
  게임 방법 시트도 `cutout`으로 넣었다 — 오려서 따로 보관하는 물건이라 오림선이
  자연스럽다. 종류를 하나 더 만들지 않았다.
- 2026-09-04 · 자산은 **경로 형식과 게임 id 일치까지만** 검증한다. 파일이 실제로
  있는지는 브라우저 런타임에서 확인할 수 없어 넣지 않았다. 아트워크 경로는
  선택 항목이라 도안 없이도 규격 검증이 통과한다 — `IDE-004`·`IDE-010`이 그림을
  그리기 전에 규격을 먼저 못 박기 위해서다.
- 2026-09-04 · 수용 기준 3번을 고쳤다. 원래 "가로 보드가 올바른 방향으로
  **렌더링된다**"였는데 렌더러는 `IDE-006`(미리보기)·`IDE-007`(내보내기)의 몫이라
  이 이슈에서 확인할 방법이 없었다. 모델이 책임지는 것 — 방향 선언과 치수 정합
  검증 — 으로 좁혔다. 실제 출력물 확인은 `IDE-007`의 수용 기준에 이미 있다.
- 2026-09-04 · 축구 예시 인스턴스의 치수·좌표는 **규격 검증용 초안**이다. 실제
  작도값은 `IDE-004`(필드·부속)와 `IDE-010`(마커·대형)이 실측으로 확정한다.
  프리셋도 4-4-2·3-5-2 두 종만 넣었다 — 나머지 2종 이상은 `IDE-010`의 몫이다.
  프리셋에 등번호 배정까지 담을지도 `IDE-010`에서 정한다(지금은 좌표만 담는다).
- 2026-09-04 · `review` → `done` 재검증. 머지된 `main`(`1c29943`)에서 `npm run typecheck`
  · `npm run build` · `npm run test:run`을 다시 돌려 전부 통과(테스트 57개)했다.
  수용 기준 8개는 각각을 겨냥한 테스트가 지키고 있다 — 파트 종류 구분, 보드의
  가로 방향과 297×210mm, 선수 슬롯 22개의 좌표 보유, 대형 프리셋 4개, 필드 범위를
  벗어난 프리셋 좌표가 걸리는지까지 확인했다. PR [#5](https://github.com/miconblog/papercraft/pull/5)로
  머지됐고, 후행 이슈(`IDE-004`·`IDE-005`·`IDE-006`·`IDE-010`)의 선행 표기에
  취소선을 그었다.
