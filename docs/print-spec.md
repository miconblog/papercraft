# 인쇄 산출 규격

`IDE-002` 기술 검증의 결론이다. `IDE-007`(인쇄·PDF 내보내기)은 이 문서를 그대로
구현하면 된다. 검증에 쓴 도구와 실측 절차는
[`spikes/print-pipeline/`](../spikes/print-pipeline/README.md)에 있다.

> **한 줄 요약** — 도안을 **코드가 만든 벡터 PDF**로 내보낸다. 브라우저 인쇄
> 대화상자는 치수를 보장하지 못한다. 배율 100%에서 운동장은 A4 한 장 크기이고,
> 가정용 프린터의 인쇄 불가 여백 때문에 **A4 2장**에 나눠 뽑는 것이 기본이다.

---

## 1. 좌표계와 단위

| 항목      | 값                                                                     |
| --------- | ---------------------------------------------------------------------- |
| 도안 단위 | **mm** (배율 100% 기준). 원점 좌상단, y는 아래로 증가 (SVG·CSS와 동일) |
| PDF 단위  | pt = 1/72 inch. `mm × 72 / 25.4`                                       |
| CSS 단위  | px = 1/96 inch. `mm × 96 / 25.4`                                       |
| 배율      | 도안 mm에 곱하는 실수. 선 굵기·글자 크기도 같이 곱한다                 |

배율을 곱하는 대상은 **좌표·크기·선 굵기·글자 크기 전부**다. 선 굵기만 고정하면
축소했을 때 도안이 시커멓게 뭉친다.

## 2. 기준 크기

- 배율 **100%에서 운동장(보드 파트)이 A4 한 장 크기** — 210×297mm(가로면 297×210mm)
- 배율은 사용자가 자유롭게 고른다. UI 프리셋은 50% · 100% · 200%
- **보드 파트와 부속 파트는 따로 뽑는다**. 파트마다 배율을 달리 줄 수 있다

**방향** — `IDE-003`이 축구 게임판의 보드를 **297×210mm 가로**로 확정했다
([docs/game-authoring.md](game-authoring.md)). 이 규격은 방향에 중립적이다 —
타일 계산이 파트 치수를 그대로 입력으로 받고, 세로든 가로든 100%는 A4 2장이다(§5 표).
검증 도안은 세로(210×297)로 만들었지만 결론은 양쪽에 그대로 적용된다.

## 3. 렌더링 방식 — 채택안

**채택: 도안(SVG 좌표계) → 코드가 생성한 벡터 PDF → 사용자가 내려받아 인쇄.**
구현은 `pdf-lib`, 글자는 **폰트 임베딩 대신 벡터 윤곽선(아웃라인)**으로 그린다.

이유:

1. **치수를 우리가 통제한다.** PDF의 MediaBox는 pt 단위 절대 크기다. 브라우저
   인쇄 대화상자의 "용지에 맞춤"·여백 설정이 끼어들 자리가 없다.
2. **브라우저와 무관하다.** 같은 코드가 같은 바이트를 만든다. Chrome·Safari·
   Firefox의 인쇄 구현 차이가 결과에 영향을 주지 않는다.
3. **벡터라서 배율에 강하다.** 200%로 뽑아도 선이 뭉개지지 않는다.
4. **아웃라인이 한글 문제를 없앤다.** `pdf-lib`의 한글 CID 폰트 임베딩은 뷰어에
   따라 글자가 깨진다(§8). 윤곽선으로 그리면 폰트 해석이 개입하지 않아 어떤
   뷰어·RIP에서도 똑같이 나오고, 파일도 오히려 작아진다.

`pdf-lib`은 Node와 브라우저 양쪽에서 같은 API로 돈다. **서버 라우트에서 생성**하는
것을 기본으로 한다 — 4.4MB짜리 한글 폰트를 사용자가 내려받지 않아도 되고, 출력이
사용자 환경과 무관하게 같아진다. 필요해지면 같은 코드를 클라이언트로 옮길 수 있다.

### 탈락안

| 후보                          | 탈락 사유                                                                                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① CSS `@page` + 브라우저 인쇄 | 도안 자체는 정확하지만(±0.016mm) **결과를 사용자의 인쇄 설정이 정한다**. 200% 시트를 A4로 뽑게 두니 경고 없이 정확히 절반으로 줄었다(§8.2). 제품의 핵심 가치를 우리가 통제하지 못하는 설정에 걸 수 없다 |
| ②-a jsPDF + `svg2pdf.js`      | 치수는 채택안과 같게 정확하다. 다만 브라우저에서만 돌아 서버 생성이 안 되고, 한글을 내려면 폰트를 굵기마다 브라우저에 등록해야 한다 — 하나를 빠뜨리면 그 글자만 조용히 깨진다(§8.5)                     |
| ③ Canvas 래스터 후 PDF 임베드 | **해상도에 종속**된다. A4 한 장이 300dpi에서 25.5MB, 600dpi는 180초 안에 생성조차 못 했다(§8.4). 확대하면 픽셀이 보이고 한글이 흐려진다                                                                 |

## 4. 인쇄 불가 여백

가정용 프린터는 용지 가장자리에 인쇄하지 못한다. 기종마다 다르고 아래쪽이 더 넓은
경우가 많다.

- 기본값 **6mm(네 변)** — 잉크젯·레이저 공통으로 안전한 쪽에 잡았다
- A4 인쇄 가능 영역 = **198 × 285mm**(세로) / **285 × 198mm**(가로)
- 사용자가 자기 프린터 값을 재서 낮출 수 있게 한다 →
  `spikes/print-pipeline/out/B2-probe-printable-area.pdf` 탐침 시트

### 무여백(테두리 없음) 인쇄를 전제하지 않는다

운동장이 A4와 같은 크기라 100%에서는 반드시 인쇄 불가 여백에 걸린다. 무여백 인쇄로
피할 수 있을 것 같지만 쓰지 않는다:

- 레이저 프린터에는 사실상 없는 기능이다
- 잉크젯의 무여백 모드는 **가장자리를 확실히 채우려고 이미지를 몇 % 확대**한다.
  이 제품이 지키려는 ±1mm를 그 확대가 그대로 깬다
- 즉 "무여백으로 A4 한 장"은 치수를 포기해야 얻는 선택지다

→ **100%의 기본은 A4 2장 분할.** A4 한 장에 담고 싶은 사용자를 위해 **"A4 한 장
맞춤(≈94%)"**를 별도 프리셋으로 제공하되, 100%가 아님을 UI에 분명히 적는다.

## 5. 타일 분할 규격

한 축을 n장으로 나눌 때 장당 도안 길이 `c`:

```
c = (L + (n-1) × V) / n          # L = 파트 길이, V = 겹침
n = ceil((L - V) / (P - V))      # P = 인쇄 가능 길이, L ≤ P 이면 n = 1
```

**겹침을 뺀 나머지를 균등 분배한다.** 마지막 장에 남는 만큼 몰아주면 겹침이 장마다
달라져 붙이는 사람이 헷갈리고, 어떤 장은 겹침이 100mm 가까이 나와 종이를 버린다.

| 항목        | 값                                                                          |
| ----------- | --------------------------------------------------------------------------- |
| 겹침 폭     | **10mm** — 손으로 자르고 붙일 때 필요한 최소 여유                           |
| 용지 방향   | 세로·가로 중 **장수가 적은 쪽을 자동 선택**, 같으면 종이를 덜 쓰는 쪽       |
| 도안 배치   | 용지 **가운데 정렬** — 네 변 여백이 고르게 남는다                           |
| 재단선      | 도안 영역 네 귀퉁이, 여백 쪽으로 4mm 실선. 맞은편 장의 재단선과 맞춰 자른다 |
| 겹침 표시   | 겹침 경계에 파선(1.5/1.5mm) + `겹침 10mm →` 라벨                            |
| 정렬 삼각형 | 겹침 경계와 마주 붙는 변에 각각 2쌍(¼·¾ 지점). 포개면 정확히 겹쳐야 한다    |
| 조립 표식   | 네 변에 `▶ 3번 오른쪽` 식으로 이웃 장 번호와 방향                           |
| 장 번호     | 하단 여백에 `보드 · 배율 200% · 3/8장 (2행 1열)`                            |
| 인쇄 안내   | 하단 여백에 `배율 100%(맞춤 없음)으로 인쇄` 고정 문구                       |

### 배율별 장수 (겹침 10mm · 여백 6mm 기준)

| 배율 | 세로 보드 210×297 | 가로 보드 297×210 |
| ---- | ----------------- | ----------------- |
| 50%  | A4 세로 1장       | A4 세로 1장       |
| 75%  | A4 세로 1장       | A4 가로 1장       |
| 100% | **A4 가로 2장**   | **A4 세로 2장**   |
| 125% | A4 가로 2장       | A4 세로 2장       |
| 150% | A4 4장            | A4 4장            |
| 200% | **A4 8장**        | **A4 8장**        |
| 300% | A4 15장           | A4 15장           |

`IDE-007`은 배율 UI에서 이 장수를 **실시간으로** 보여 준다. 200%가 8장이라는 걸
뽑기 전에 알아야 한다.

## 6. 부속 별지 표기 규약

| 표시   | 그리는 법                      | 뜻                    |
| ------ | ------------------------------ | --------------------- |
| 오림선 | 실선 0.25mm                    | 선 위를 그대로 자른다 |
| 골접기 | 파선 dash 2mm / gap 1.5mm      | 안쪽으로 접는다       |
| 산접기 | 일점쇄선 4 / 1.2 / 0.6 / 1.2mm | 바깥쪽으로 접는다     |
| 풀칠면 | 45° 해칭 0.12mm, 간격 1.5mm    | 풀을 바르는 면        |

- **최소 선 굵기 0.12mm.** 그보다 얇으면 가정용 프린터에서 끊긴다
  (실제 하한은 `B2-accessory-tiled-100.pdf`의 굵기 눈금으로 기종별 확인)
- 색에 의존하지 않는다 — 흑백 프린터에서도 네 가지가 구분되어야 한다

## 7. 한글 폰트

- 서체: **Noto Sans KR**(OFL). 저장소에 파일로 두고 생성 시점에 읽는다
- **글자는 윤곽선(패스)으로 그린다.** 폰트를 PDF에 임베딩하지 않는다
- 굵기별로 폰트 파일을 각각 둔다(Regular / Bold). 합성 볼드는 쓰지 않는다
- 글자가 패스가 되면 PDF에서 텍스트 선택·검색이 안 된다. 게임판에는 문제가 안 되지만,
  게임 방법 별지처럼 문장이 긴 파트가 늘면 이 결정을 다시 본다

## 8. 검증 결과

수치는 `spikes/print-pipeline/out/measure-report.md`(디지털 실측)와
`out/font-report.md`(폰트)에서 자동 생성된다. 종이 실측은
`spikes/print-pipeline/README.md`의 체크리스트로 사람이 채운다.

### 8.1 도안 좌표 → 종이 mm (단일 시트, Ghostscript 600dpi 실측)

측정 구간은 검증 도안에 박아 둔 측정점 A↔B(도안상 150mm)와 C↔D(도안상 200mm)다.

| 후보                          | 50%      | 100%     | 200%      | 페이지 상자(100%)   |
| ----------------------------- | -------- | -------- | --------- | ------------------- |
| **② pdf-lib (채택)**          | ±0.009mm | ±0.006mm | ±0.008mm  | **210.000×297.000** |
| ② jsPDF + svg2pdf.js          | ±0.009mm | ±0.006mm | ±0.008mm  | 210.000×297.000     |
| ①′ 헤드리스 Chrome(설정 고정) | ±0.005mm | ±0.016mm | ±0.005mm  | 209.89×297.01       |
| ③ Canvas 래스터 300dpi        | —        | ±0.012mm | 생성 실패 | 210.000×297.000     |

- 세 방식 모두 **도안 안의 치수는 정확하다.** 갈리는 것은 그 다음이다.
- Chrome이 만든 PDF는 **페이지 상자가 0.1~0.2mm 어긋난다**(210mm 요청 → 209.89mm).
  도안은 맞지만 종이 크기 자체가 반올림된다. `pdf-lib`은 소수 셋째 자리까지 정확했다.

### 8.2 사용자 인쇄 설정이 결과를 흔드는 정도

앱이 만든 페이지 크기와 사용자가 고른 용지가 다르면 **브라우저가 말없이 배율을 바꾼다.**

| 시트                   | 지정 A↔B |      실측 A↔B | 결과                             |
| ---------------------- | -------: | ------------: | -------------------------------- |
| 100%(210×297) → A4     |    150mm |     150.006mm | 우연히 용지와 같아 그대로 나온다 |
| **200%(420×594) → A4** |    300mm | **150.028mm** | **정확히 절반으로 줄었다**       |
| 50%(105×148.5) → A4    |     75mm |      74.993mm | 크기는 맞고 A4 가운데에 놓인다   |

200%를 뽑으려던 사용자가 100%짜리를 받는다. **경고도 없다.** 후보 ①을 쓰지 않는
이유가 이것이다 — 우리가 아무리 잘 그려도 결과는 사용자의 인쇄 대화상자가 정한다.

> 이 실험은 CDP로 용지 크기만 어긋나게 해 재현한 것이다. 실제 대화상자에는
> "용지에 맞춤" · 배율 % · 여백 프리셋이 더 있어 어긋날 경로가 더 많다.

### 8.3 타일 이음

`B2-board-tiled-200.pdf`(A4 8장)의 이음 11곳 전부에서 **정합 오차 0.000mm**
(300dpi 래스터 기준, 1픽셀 = 0.085mm). 타일을 계획대로 이어 붙인 뒤 다시 잰
치수도 A↔B 300.19mm / C↔D 400.00mm로 **±0.2mm 안**이다.

### 8.4 후보 ③(Canvas 래스터)이 탈락한 이유 — 용량과 시간

| 조건             | 결과                     |
| ---------------- | ------------------------ |
| A4 100% · 150dpi | 6.4MB                    |
| A4 100% · 300dpi | **25.5MB**               |
| A4 100% · 600dpi | **180초 안에 생성 실패** |
| 200% · 300dpi    | **180초 안에 생성 실패** |

같은 도안이 `pdf-lib` 벡터로는 **25KB**다. 1000배 차이다. 게다가 래스터는 확대할수록
픽셀이 드러나고, 한글 라벨이 흐려진다.

### 8.5 한글 폰트

`pdf-lib`의 한글 CID 폰트 임베딩은 **뷰어마다 다르게 깨진다**:

| 방식                  | Ghostscript  | macOS 미리보기 |    PDF 용량 |
| --------------------- | ------------ | -------------- | ----------: |
| 폰트 임베딩(서브셋)   | ❌ 일부 깨짐 | ❌ 완전히 깨짐 |     44.7 KB |
| 폰트 임베딩(전체)     | ❌ 깨짐      | ❌ 완전히 깨짐 |      3.7 MB |
| **벡터 윤곽선(채택)** | ✅ 정상      | ✅ 정상        | **25.2 KB** |

서브셋 임베딩은 **불안정하다** — 다섯 줄짜리 표본 문서는 미리보기에서 정상이었는데
같은 코드로 만든 실제 도안은 깨졌다. "되는 것처럼 보이다가 특정 문서에서 깨지는"
쪽이 제일 나쁘다. 윤곽선은 그 변수를 통째로 없애고 파일도 더 작다.

폰트 파일 자체는 Noto Sans KR 정적 OTF 4.4MB, 가변 TTF 9.9MB이며 **생성 시점에만**
필요하다(사용자에게 내려보내지 않는다).

후보 ②-a(jsPDF + svg2pdf.js)로도 한글은 낼 수 있지만, **폰트를 굵기마다 브라우저에
등록**하고 SVG의 `font-family`를 그 이름과 맞춰야 한다. 이번 실험에서 Regular만
등록했더니 본문은 정상이고 **굵은 제목만 조용히 깨졌다.** 폰트를 브라우저로
내려보내야 하는 비용도 그대로 남는다 — TTF 9.9MB(base64 13.2MB)를 페이지에 실었고
PDF 한 장 생성에 17.5초가 걸렸다(결과 PDF는 0.10MB로, jsPDF가 서브셋은 해 준다).

## 9. 지원 브라우저와 사용자에게 안내할 인쇄 설정

PDF를 코드가 만들기 때문에 **브라우저는 도안 미리보기와 파일 내려받기만** 담당한다.
치수는 브라우저가 아니라 **PDF 뷰어의 인쇄 설정**에 달려 있다.

| 브라우저 | 지원 | 필요한 것                       |
| -------- | ---- | ------------------------------- |
| Chrome   | 지원 | 내려받기 후 PDF 뷰어에서 인쇄   |
| Edge     | 지원 | 〃                              |
| Safari   | 지원 | 〃 (macOS 미리보기가 기본 뷰어) |
| Firefox  | 지원 | 〃                              |

**사용자에게 반드시 노출할 인쇄 설정** — 내보내기 화면과 PDF 첫 장 여백에 함께 적는다:

- 크기 **실제 크기 / 100%** — "용지에 맞춤(Fit to page)"을 **끈다**
- "자동 회전 및 가운데 맞춤" **끔**
- 용지 **A4**
- 프린터 드라이버의 축소·확대, **테두리 없음(무여백) 끔**
