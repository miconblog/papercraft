# 자체 웹 분석

어떤 게임을 더 만들지, 공유 기능이 정말 필요한지는 **조회수와 PDF 다운로드수**가
답한다. GA 를 붙이지 않고 직접 만든 이유는 두 가지다 — 아이와 함께 쓰는 사이트라
제3자에게 방문 기록을 넘기지 않는 편이 낫고, 필요한 지표가 좁아 범용 도구가 과하다.

이슈: `issues/IDE-013-self-hosted-web-analytics.md`

## 이 프로젝트는 Supabase 를 남과 나눠 쓴다

같은 Postgres 에 `lylo_app` · `rlibro_*` 등 **다른 서비스의 스키마가 실제로 있다.**
그래서 아래 두 가지가 절대 규칙이다.

- 우리 것은 **`daddys_craft` 스키마 하나**뿐이다. `public` · `auth` · `storage` 는
  읽지도 고치지도 않는다.
- **Supabase CLI 를 쓰지 않는다.** `supabase db reset` 은 남의 데이터를 통째로
  날리고, `supabase db push` 는 이력의 주인이 다른 저장소인 `supabase_migrations`
  를 두 저장소가 다투게 만든다.

## 처음 한 번만 하는 설정

### 1. 환경변수

```bash
cp .env.example .env.local   # 값은 .env.example 의 설명대로 채운다
```

없거나 비어 있으면 **수집이 조용히 꺼진다.** 로컬과 CI 는 키 없이 돌아야 한다.

### 2. 대시보드에서 스키마를 노출한다 ⚠️ 이것을 빼면 아무것도 안 쌓인다

> Supabase 대시보드 → **Settings → API → Exposed schemas** → `daddys_craft` 추가

`supabase-js` 는 PostgREST 를 거치고, PostgREST 는 **이 목록에 있는 스키마만
본다.** 서비스 롤 키로도 우회되지 않는다 — 서비스 롤은 RLS 를 우회할 뿐 이
목록을 우회하지는 못한다. 빠뜨리면 서버 로그에 이렇게 남는다:

```
[analytics] 이벤트 기록 실패: "Invalid schema: daddys_craft"
```

기존 목록에 **더하기만** 하므로 다른 서비스에는 영향이 없다.

노출되는 만큼 **RLS 가 보험이 아니라 본선이 된다.** 그래서 `events` 를 비롯한
모든 표에 RLS 를 켜고 **정책을 하나도 만들지 않는다** — 정책이 없으면 RLS 를
우회하는 서비스 롤 외에는 전부 막힌다. "insert 만 허용" 같은 정책을 하나 두면
그 구멍으로 누구나 가짜 이벤트를 밀어 넣을 수 있다. 여기에 더해 `anon` ·
`authenticated` 롤에서 스키마 권한 자체를 회수해 이중으로 잠근다.

### 3. 스키마를 적용한다

```bash
npm run db:migrate                        # 적용
npm run db:migrate -- --dry               # 무엇이 적용될지만 본다
npm run db:migrate -- --redo <파일명>     # 이미 적용한 파일을 한 번 더
```

`db/migrations/NNN-*.sql` 을 번호 순서대로 `psql` 로 넣고, 적용 이력을
**우리 스키마 안**(`daddys_craft.migrations`)에 남긴다. 한 파일 = 한 트랜잭션이라
중간에 실패하면 그 파일은 통째로 되돌아간다.

적용기는 파일에 `public` · `auth` · `storage` 가 **낱말로 한 번이라도 나오면
전부 거부한다.** 공유 DB 에서는 실수 한 번의 대가가 우리 쪽에만 그치지 않아,
"위험한 문장만" 정교하게 가려내기보다 무디게 막는 편이 낫다.

### 4. 정리 일감

`002` 가 pg_cron 에 하루 한 번 도는 일감을 건다 — 매일 **15:10 UTC(= KST 자정
10분 뒤)** 에 `daddys_craft.run_daily_maintenance()` 를 부른다. 그날치가 다 들어온
뒤에 최근 사흘을 다시 집계하고 365일 지난 원본을 지운다.

```bash
psql "$SUPABASE_DB_URL" -c "select jobname, schedule, active from cron.job \
  where jobname = 'daddys_craft_daily_maintenance';"
```

pg_cron 이 없으면 `002` 는 알림만 남기고 넘어간다 — **확장을 켜는 것은 공유
프로젝트 전체에 걸리는 변경이라 마이그레이션이 스스로 하지 않는다.** 나중에 켰다면
그 파일을 한 번 더 돌려야 하는데, 이미 이력에 있어서 평범한 `db:migrate` 는
건너뛴다. 그래서 플래그가 있다:

```bash
npm run db:migrate -- --redo 002-daily-maintenance-schedule.sql
```

이름이 같은 **우리 일감만** 지우고 다시 걸므로 몇 번을 돌려도 하나다.

일감이 없는 동안에도 화면 숫자는 맞다 — 대시보드가 열릴 때마다 최근 사흘을 다시
집계한다. 밀리는 것은 원본 정리 하나뿐이고, `select
daddys_craft.run_daily_maintenance()` 로 언제든 손으로 돌릴 수 있다.

## 무엇을 저장하고 무엇을 버리는가

| 저장한다                                     | 저장하지 않는다                    |
| -------------------------------------------- | ---------------------------------- |
| `visitor_id` — 그날치 salt 로 만든 해시      | IP 원본                            |
| `ua_browser` · `ua_os` · `ua_device`         | 전체 User-Agent 문자열             |
| `referrer_host` — 호스트만                   | referrer 전체 URL(검색어까지)      |
| `path` — 물음표 앞까지                       | 쿼리 문자열                        |
| `utm_source` · `utm_medium` · `utm_campaign` | 쿠키(하나도 심지 않는다)           |
| `lang` — 언어 코드 하나(`ko` · `de`)         | 지역과 언어 목록(`de-AT,en;q=0.8`) |
| `bot_score` · `bot_reason` — 봇 신호와 근거  | 판정에 쓴 헤더 원본                |

`visitor_id = HMAC(그날의 salt, IP + UA + 도메인)` 이고 salt 는 자정(KST)에
바뀐다. 되돌릴 수 없고, 날이 바뀌면 같은 사람이라도 다른 값이 된다.

### 그래서 UV 는 "일간" 순방문자다

같은 사람이 사흘 오면 **3명으로 센다.** 주간·월간 UV 는 정확하지 않고 대략치로만
읽어야 한다 — 화면에도 그렇게 적어 두었다. 정확한 재방문율이 필요해지면 그때
동의 배너와 함께 다시 본다.

`session_id`(30분 무활동이면 새로)는 UV 와 다른 것을 말해 준다. 세션 수와 세션당
페이지 수는 여기서 나온다.

## 어디서 무엇이 기록되나

| 무엇         | 어디서                                                                 | 왜 거기서                                                                                             |
| ------------ | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 페이지뷰     | `src/components/analytics/PageViews.tsx` → `POST /api/analytics/event` | App Router 는 첫 로드 뒤로 문서를 새로 받지 않는다 — `usePathname()` 을 봐야 클라이언트 전환이 잡힌다 |
| PDF 다운로드 | `/api/games/[id]/export` 에서 **서버가 직접**                          | 클라이언트 이벤트는 차단기와 이탈로 빠진다                                                            |

브라우저가 보내는 것은 **경로와 referrer 뿐**이다. 방문자 해시·채널·국가는 전부
서버가 헤더에서 만든다 — 클라이언트가 정할 수 있으면 누구나 원하는 숫자를 만들어
넣을 수 있다.

수집은 **응답을 절대 붙잡지 않는다.** Supabase 가 죽어 있어도, 키가 없어도,
스키마가 노출돼 있지 않아도 페이지와 PDF 는 그대로 나가고 서버 로그에 경고만
남는다.

## 봇은 두 겹으로 거른다

| 겹                       | 무엇을 보나                                    | 처분                            |
| ------------------------ | ---------------------------------------------- | ------------------------------- |
| `request.ts`의 UA 정규식 | `bot` · `crawl` · `spider` 처럼 스스로 밝힌 것 | **줄을 안 만든다**              |
| `bot.ts`의 점수          | 사람인 척하는 자동화의 신호                    | 줄은 남기고 **집계에서만 뺀다** |

두 번째 겹의 처분이 다른 이유는 판정이 확률적이기 때문이다. 같은 방식으로 줄을
지우면 **진짜 사람을 조용히 지워 놓고 알아채지 못한다.** 점수를 남겨 두면
원본에서 무엇이 걸렸는지 보이고, 기준을 고쳐 `rollup_daily` 를 다시 돌리는 것만으로
지난 날짜까지 새 기준으로 따라온다.

| 신호                 | 점수 | 왜                                                                    |
| -------------------- | ---- | --------------------------------------------------------------------- |
| `no-accept-language` | 2    | 진짜 브라우저는 늘 보낸다. 없으면 HTTP 클라이언트를 손으로 짠 것이다  |
| `no-client-hints`    | 1    | UA 는 Chrome 인데 `sec-ch-ua` 가 없다 — 위장 신호. **아래 주의 참고** |
| `bad-fetch-metadata` | 3    | 우리 페이지의 `fetch` 라면 `same-origin`/`cors` 여야 한다             |

문턱은 **2**다. 앱(`BOT_THRESHOLD`)과 SQL(`rollup_daily` 의 기본 인자) 두 곳에
같은 값이 있다 — 앱은 참고용이고 **실제로 거르는 것은 SQL 쪽**이다.

> ⚠️ `no-client-hints` 에 1점만 준 것은 **`sec-ch-ua` 가 브라우저의 `fetch`
> 요청에도 실리는지 실물로 확인하지 않았기 때문**이다. 가정이 틀렸다면 이
> 신호 하나로 Chrome 사용자 전부가 봇이 되므로, 혼자서는 문턱을 못 넘게 뒀다.
> 실제 방문이 쌓이면 `bot_reason` 을 세어 확인하고 가중치를 정한다.

```sql
-- 무엇이 봇으로 걸렸나 (대시보드 SQL Editor 에서)
select bot_score, bot_reason, ua_browser, ua_os, country, lang, count(*)
from daddys_craft.events
where day >= current_date - 7
group by 1,2,3,4,5,6 order by count(*) desc;

-- 기준을 바꿔 다시 집계한다
select daddys_craft.rollup_daily(current_date - 30, current_date, 3::smallint);
```

## 보기

`/admin/analytics` — 최근 30일 PV/UV 추이, 채널 구성, 게임별 조회·다운로드.

관리자가 한 명뿐이라 `ANALYTICS_ADMIN_PASSWORD` 하나로 잠근다. Supabase Auth 를
붙이면 사용자 표·세션·비밀번호 재설정까지 딸려 오는데, 쓸 사람이 한 명이면 전부 짐이다.
대신 세 가지는 지킨다.

- 비교를 `timingSafeEqual` 로 한다 — 문자열 `===` 는 몇 글자까지 맞았는지가
  응답 시간에 새어 나온다.
- 비밀번호가 설정돼 있지 않으면 401 이 아니라 **404** 다. 경로의 존재 자체를 숨긴다.
- proxy(`src/proxy.ts`)와 페이지가 **각자** 확인한다. matcher 를 잘못 건드리거나
  경로를 옮기면 proxy 검사가 조용히 사라지는데, 그때 통계가 그대로 열리면
  아무도 눈치채지 못한다.

### 공유 링크 만들기

같은 화면 아래에 utm 링크 빌더가 있다. 페이스북·인스타그램·링크드인이 기본으로
있고, `직접 입력` 으로 아무 `utm_source`/`utm_medium` 이나 쓸 수 있다.

손으로 `?utm_source=…` 를 조립하면 어느 날은 `facebook`, 어느 날은 `fb` 가 되어
**한 채널이 표에서 둘로 쪼개진다.** 만드는 곳을 하나로 두는 이유다. 값은 소문자로
눌리고 빈칸은 `-` 가 된다 — 한글은 살린다(`여름방학` 같은 캠페인 이름이 조용히
사라지면 안 된다).

만든 링크가 **위 표의 어느 칸에 쌓일지**를 그 자리에서 보여 준다. 수집 쪽과 같은
`classifyChannel` 로 판정하므로 화면이 거짓말을 할 수 없다 — 그 거짓말은 몇 주 뒤
숫자를 볼 때까지 드러나지 않는다.

링크의 앞부분은 `NEXT_PUBLIC_SITE_URL` 이다. 그 값이 없을 때만 지금 보고 있는
호스트로 떨어진다 — **미리보기 배포에서 어드민을 열고 링크를 만들면 미리보기
주소를 세상에 뿌리게 된다.**

세션은 서버에 남기지 않는다. 만료 시각에 서명한 쿠키 하나뿐이고, 서명 키를
비밀번호에서 유도하므로 **비밀번호를 바꾸면 이미 나간 쿠키가 전부 무효가 된다.**

## 보관 기간

원본 이벤트 **365일**, 일자별 집계는 **영구**.

원본이 있어야 나중에 생긴 질문("축구를 본 사람 중 몇 %가 PDF 를 받았나")에 답할
수 있다. 한 줄 300바이트로 하루 1,000 PV 여도 월 10MB 안팎이라 무료 티어(500MB)에
1년은 넉넉하고, 1년이면 방학·학기 같은 계절성까지 보인다.

집계를 **뷰가 아니라 표로** 만든 것이 이 때문이다. 뷰였다면 원본을 지우는 순간
1년 전 그래프가 통째로 0 이 된다. `purge_events()` 는 지우기 전에 지울 구간을
반드시 한 번 더 집계하고, `rollup_daily()` 는 원본이 이미 없는 날에는 손대지 않는다.
