# 도안 작성 규격

이 문서는 `src/lib/schema`가 강제하는 규격을 사람 말로 옮긴 것이다. 규격을 어긴
도안은 등록되는 순간 예외로 터지므로, 여기 적힌 것과 코드가 어긋나면 **코드가
맞다** — 그때는 이 문서를 고친다.

## 새 게임 추가 — 3단계

1. **도안 파일을 만든다** — `src/assets/games/<게임 id>/index.ts`에서
   `defineGame({ … })`을 `export default` 한다. 본보기는
   [`src/assets/games/soccer/index.ts`](../src/assets/games/soccer/index.ts)다.
2. **등록한다** — [`src/lib/games/registry.ts`](../src/lib/games/registry.ts)에
   import를 더하고 `definitions` 배열에 넣는다. 아트워크를 코드로 만든다면
   [`scripts/build-artwork.mts`](../scripts/build-artwork.mts)의 `ARTWORK_BY_GAME`
   에도 한 줄을 더한다.
3. **검증한다** — `npm run test:run`. 규격을 어겼으면 어느 칸이 왜 틀렸는지
   한국어로 나온다.

정적 자산(썸네일·SVG)은 `public/games/<게임 id>/` 아래에만 둔다. 다른 게임 폴더를
가리키면 검증에서 걸린다.

도안 SVG는 **코드로 만드는 것을 권한다.** 슬롯 좌표와 그림이 같은 치수 상수를
읽어야 어긋나지 않는다. 네 게임이 다 그렇게 되어 있다 —
`src/assets/games/<게임 id>/dimensions.ts`에 치수를 모으고 `artwork/`가 SVG를
지으며 `npm run artwork [게임 id]`가 `public/`에 쓴다. 자세한 것은
[docs/soccer-artwork.md](soccer-artwork.md) 1절,
[docs/baseball-artwork.md](baseball-artwork.md) 1절,
[docs/world-tour-artwork.md](world-tour-artwork.md) 1절,
[docs/yut-nori-artwork.md](yut-nori-artwork.md) 1절,
[docs/dot-to-dot-artwork.md](dot-to-dot-artwork.md) 1절.

### 도안이 실행 시점에 생성되는 게임

여기까지는 **인쇄물의 형태가 저장소 안에 있는** 게임이다. 사용자는 이름·색·마커
자리를 고치고, 그 값이 미리 그려 둔 SVG 위에 얹힌다.

점 잇기(`IDE-019`)는 다르다 — **인쇄물의 형태 자체가 사용자가 넣은 사진에서
나온다.** 가리킬 SVG 파일이 없다. 이런 게임을 더할 때 밟을 것이 셋이다.

1. **계산을 순수 함수로 뗀다.** `src/lib/<게임 id>/`에 두고 DOM에도 서버에도
   매지 않는다. 브라우저(입력을 다루는 쪽)와 서버 렌더러가 같은 코드를 쓰고,
   테스트가 원자료를 직접 넣을 수 있다.
2. **생성된 값을 슬롯에 담는다.** 도안이 후보를 미리 선언할 수 없는 값이면
   `outline` 같은 슬롯 종류를 쓴다(아래 「윤곽 슬롯」). 커스터마이즈에 실려
   저장·복원·전송되는 것은 이 값 하나뿐이어야 한다.
3. **파트에 `dynamic`을 둔다.** 그러면 아트워크를 읽는 자리 둘 —
   미리보기(`BoardPreview`)와 내보내기(`composeExport`의 `loadArtwork`) — 이
   자동으로 렌더러 쪽으로 바뀐다. **게임 정의가 SVG를 직접 들고 다니게 만들지
   않는다.** 그렇게 하면 다른 게임의 정적 자산 규약이 함께 흔들린다.

정적 `artwork` 파일은 **그래도 만들어 커밋한다.** 기본값으로 그린 한 벌이고,
카탈로그 썸네일과 소개 페이지가 그것을 쓰며, 생성기가 깨졌을 때 산출 SVG의
차이로 그것을 알아채는 자리이기도 하다.

게임에 매이지 않는 그리기 도구는 [`src/assets/shared/`](../src/assets/shared)에
있다. `svg.ts`가 SVG 문자열을 짓고(표시 레이어·빗금·글자 폭 어림), `figure.ts`가
관절 각도에서 사람 그림을 짓는다 — 관절을 도형으로 부풀리고, 마커 상자에 맞춰
넣고, 모서리를 둥글리는 일이 거기 있다. **종목이 갖는 것은 거기 두지 않는다**:
몸 비율·자세 각도·부위를 쌓는 차례는 게임마다 다르고, 그 차이가 그림을 종목처럼
보이게 한다(축구는 반바지에 맨머리, 야구는 긴 바지에 모자다).

## 좌표계와 단위

- 단위는 **mm**다. 배율 100%에서 mm 값이 그대로 종이 위 실측 치수가 된다.
- 원점은 **파트의 좌상단**, x는 오른쪽, y는 아래다(SVG·CSS와 같다). PDF는 원점이
  좌하단이지만 뒤집는 일은 렌더러가 한다 — 도안 데이터는 뒤집지 않는다.
- 좌표는 언제나 **파트 로컬**이다. 용지 위 배치(여백·타일 분할)는 인쇄 규격
  (`IDE-002`)의 몫이고 도안은 그것을 모른다.

## 마커 스타일 변형

같은 슬롯을 여러 모습으로 그린다. 변형끼리 크기는 달라도 된다 — 기준점이 마커
**중심**이라 바꿔 끼워도 배치가 어긋나지 않고, 겹침 검사는 세트에서 가장 큰
변형을 쓴다.

`filled`는 **마커 안이 그룹 색으로 채워지는지**다. 렌더러는 마커 아트워크의
`pc-marker-team` 레이어에 그룹 색을 `fill`·`stroke` 양쪽으로 칠하는데, 어느 쪽이
실제로 보이는지는 도안이 그린 도형에 달렸다 — 축구 게임판의 빈 원과 색칠용
윤곽선은 테두리만, 실루엣은 채움만 받는다.

이 값이 필요한 이유는 **값(등번호) 색** 때문이다. 채워진 마커는 배경이 그룹
색이라 밝기에 맞춰 반전해야 읽히고, 채우지 않는 마커는 배경이 흰 종이라 그룹
색을 그대로 써야 한다. 반대로 쓰면 흰 배경에 흰 글자가 찍힌다.

## 게임 방법 (`rules`)

규칙문은 도안 정의가 들고 있다. 블록 종류는 셋뿐이다 — `heading`(절 제목) ·
`step`(번호 붙는 항목) · `bullet`(점 항목). 소개 페이지(`/games/[id]`)가 이 값을
읽어 절 단위로 그린다.

**인쇄 파트에 매지 않는다.** 축구 게임판은 오래 규칙을 `rules-card` 파트로 뽑았는데,
그 장을 출력물에서 빼자 규칙이 갈 곳이 없어졌다(2026-09-05). 어느 파트를 뽑든
규칙은 읽을 수 있어야 한다 — 그래서 파트가 아니라 게임의 필드다. 규칙 카드를
원하는 게임은 이 값을 읽어 부속을 그리면 된다. 윷놀이가 그렇게 한다
(`src/assets/games/yut-nori/artwork/rules-sheet.ts`) — 규칙이 길고 놀면서 자꾸
되짚는 게임이라 판 옆에 둘 종이가 있어야 했다. 값은 여전히 `rules` 필드 하나이고
부속은 그것을 조판할 뿐이다.

마크다운은 받지 않는다. 렌더러가 커지고, 인쇄물로 조판할 때 다룰 수 없는 문법이
섞인다.

## 파트

게임은 종이 한 장이 아니다. **보드 1개 + 부속 N개**로 나뉘고, 사용자는 파트를
따로, 서로 다른 배율로 뽑는다.

| `kind`      | 뜻                 | 필요한 표시                   |
| ----------- | ------------------ | ----------------------------- |
| `board`     | 핵심 게임판        | 없다 (오리지도 접지도 않는다) |
| `cutout`    | 오려 쓰는 부속     | `cut`                         |
| `buildable` | 접어 세우는 조립물 | `cut` + 접는선 하나 이상      |

- `orientation`은 치수와 일치해야 한다. 가로(`landscape`)로 선언하면
  `widthMm >= heightMm`여야 한다. 축구 게임판의 보드는 297×210mm 가로다.
- `minScale`·`maxScale`은 그 파트가 **읽히는** 배율 범위다. 규칙 텍스트가 든
  부속은 보드보다 하한이 높다. 실측으로 정한다.
- `defaultCopies`는 '몇 벌' 기본값이다. 잃어버리기 쉬운 작은 부속은 1보다 크게
  잡는다.
- `regions`는 파트 안의 이름 붙은 사각형이다. 마커가 움직일 수 있는 범위를 여기로
  제한한다.

### 동적 파트 — 아트워크를 값에서 그때 그리는 파트

`dynamic`을 두면 아트워크는 정적 파일이 아니라 **값에서 그때 그린 SVG**다
(`IDE-016` 2단계). 세계일주 게임판이 처음 쓴다 — 목록 슬롯 `cities`가 켠 도시와
그 차례를 들고, 서버 렌더러가 그 값에서 판을 그린다.

```ts
dynamic: {
  listSlotId: 'cities',        // 이 파트에 control 배치를 가진 list 슬롯
  frameSlotId: 'board-frame',  // (선택) choice 슬롯. 값이 'map'이면 지도만
  sizeSteps: [                 // 켠 항목 수 → 판 크기. maxItems 오름차순, 마지막은 그 위 전부
    { maxItems: 50, widthMm: 297, heightMm: 210, mapHeightMm: 150.62 },
    { maxItems: 70, widthMm: 420, heightMm: 297, mapHeightMm: 213.01 },
    { maxItems: 100, widthMm: 594, heightMm: 420, mapHeightMm: 301.24 },
  ],
}
```

**`listSlotId`·`sizeSteps`는 함께 적거나 함께 비운다.** 비우면 크기가 파트 선언
그대로 고정이고 **그림만 값에서 나온다** — 점 잇기 판(`IDE-019`)이 그렇다. 사진이
무엇이든 판은 190×277 한 장이고 바뀌는 것은 그 위의 점과 번호뿐이다.

```ts
dynamic: {
} // 크기 고정. 그림을 정하는 값은 control 배치가 말한다
```

- **무엇이 그림을 바꾸는지는 파트에 따로 적지 않는다.** 그 파트에 `control`
  배치를 가진 슬롯이 곧 그것이다(`dynamicSourceSlots`). `control`의 뜻이 원래
  "그려지지는 않지만 그 파트의 렌더링을 바꾸는 값"이라, 같은 사실을 두 곳에
  적으면 슬롯을 더할 때 한쪽만 고쳐 미리보기가 안 따라오는 일이 생긴다.
  미리보기는 **이 값들이 바뀔 때만** 서버에 판을 다시 청한다 — 말 이름이나 색은
  여기 들지 않으므로 글자를 한 자 칠 때마다 요청이 나가지 않는다.
- 동적 파트인데 `control` 배치를 가진 슬롯이 하나도 없으면 검증이 막는다. 값이
  아무리 바뀌어도 늘 같은 그림이라 동적일 이유가 없다.
- **크기는 데이터로, 그림은 코드로.** 도안 정의는 서버에서 클라이언트로 그대로
  넘어가는 데이터라 함수를 실을 수 없다. 크기(`sizeSteps`)는 스키마가 계산해
  에디터·인쇄 옵션이 바로 쓰고(`resolvePart` · `dynamicSize`), 그림은 게임 id별
  렌더러를 [`src/lib/games/dynamic-artwork.ts`](../src/lib/games/dynamic-artwork.ts)에
  등록한다. **서버에서만 부른다** — 미리보기는 `POST /api/games/<id>/artwork`로
  받고 내보내기는 같은 함수를 직접 부른다. 두 길이 같은 함수라 화면과 PDF가
  같은 그림이다.
- 렌더러가 그린 SVG의 크기는 스키마가 계산한 크기와 같아야 한다. API와
  내보내기가 확인한다.
- `artwork`는 그대로 둔다 — 기본값으로 그린 정적 파일이고 카탈로그 썸네일이
  쓴다.
- 목록 슬롯은 에디터에서 한 줄 입력이 아니라 **판 아래 패널**(`ListSlotPanel`)
  이다 — 켜고 끄고 차례를 바꾸며, 켜면 전체 목록 차례에서 바로 앞에 켜진 항목
  뒤에 끼어든다.
- `custom: true`면 값에 옵션 밖의 항목(`{ id, label, data }`)이 올 수 있다 —
  세계일주가 검색해서 더한 도시의 이름·경위도를 이렇게 싣는다. `data`의 뜻은
  게임 렌더러가 안다. `search.providerId`를 두면 패널에 검색 상자가 붙고, 질의는
  `GET /api/games/<id>/list-search?slot=&q=`로 가서 서버 제공자
  ([`src/lib/games/list-search.ts`](../src/lib/games/list-search.ts))가 답한다.
  결과는 옵션 id이거나 값에 실릴 새 항목이다.

### 파트 변형 — 선택에 따라 크기와 아트워크가 바뀌는 파트

`variants`를 두면 **`choice` 슬롯의 값에 따라 파트의 치수·아트워크·제목이 바뀐다**
(`IDE-016` 1단계). 미리 그려 둔 SVG 몇 벌 사이를 오갈 때 쓴다 — 세계일주
게임판이 도시 수 프리셋으로 잠깐 썼다가, 개별 도시를 켜고 끄게 되면서 동적
파트로 옮겨 갔다. 지금 쓰는 게임은 없지만 "판 크기 A4/A3 중 택일" 같은 데
그대로 쓸 수 있다.

```ts
variants: {
  selectorSlotId: 'city-count',        // 이 파트에 control 배치를 가진 choice 슬롯
  options: [
    { value: 'cities-50', title: '게임판 · 도시 50개 (A4)', widthMm: 297, heightMm: 210, artwork: '/games/world-tour/board.svg' },
    { value: 'cities-60', title: '게임판 · 도시 60개 (A3)', widthMm: 420, heightMm: 297, artwork: '/games/world-tour/board-60.svg' },
    // …
  ],
}
```

- 선택지 값은 선택 슬롯의 `options`와 **정확히 같아야** 한다(마커 스타일 세트의
  `selectorSlotId`와 같은 규칙).
- **기본값 변형은 파트 자체와 같아야 한다.** 선택 슬롯을 모르는 곳(카탈로그
  썸네일·소개 페이지)이 보는 파트가 곧 기본값이다.
- 변형은 파트의 인쇄 방향을 바꾸지 못한다.
- 파트를 읽는 코드는 `resolvePart(game, part, customization)`를 거친다 — 렌더러·
  에디터 미리보기·인쇄 옵션이 전부 그렇다. 원본 파트를 그대로 쓰는 곳이 하나라도
  있으면 화면과 인쇄물의 크기가 어긋난다.

## 슬롯

슬롯은 도안 안에 선언된 "사용자가 고칠 수 있는 자리"다. 두 축을 갖는다.

**값의 종류(`kind`)** — 에디터가 이걸 보고 입력 컴포넌트를 고른다.

| `kind`    | 제약                                                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `text`    | `maxLength`                                                                                                                           |
| `number`  | `min` · `max` · `integer`                                                                                                             |
| `color`   | `#RRGGBB`, 선택적으로 `palette`                                                                                                       |
| `choice`  | `options` 2개 이상                                                                                                                    |
| `list`    | `options`의 항목 id를 **차례 있게** 고른 배열. `fixed` · `min` · `presets` · `custom`(옵션 밖 항목 허용) · `search`(서버 검색 제공자) |
| `outline` | `[x0, y0, x1, y1, …]` 납작한 mm 좌표의 **닫힌 폴리라인**. `minPoints` · `maxPoints`                                                   |

기본값(`default`)은 자기 제약을 지켜야 한다. 지키지 않으면 에디터가 첫 화면부터
오류 상태로 시작하므로 검증에서 막는다.

**나타나는 방식(`placements`)** — 슬롯 하나가 여러 파트에 놓일 수 있다. 팀 이름은
보드에도 점수 기록칸에도 나온다. 최소 1개가 있어야 한다 — 어느 파트에도 속하지
않는 슬롯은 도안에 나타날 자리가 없다.

| `mode`    | 뜻                                 | 쓸 수 있는 `kind`                        |
| --------- | ---------------------------------- | ---------------------------------------- |
| `text`    | 값을 글자로 그린다                 | `text` · `number`                        |
| `marker`  | 값을 마커로 그린다 (좌표를 갖는다) | `text` · `number`                        |
| `paint`   | 값을 도안 레이어의 색으로 칠한다   | `color`                                  |
| `control` | 그려지지 않고 렌더링을 바꾼다      | `choice` · `list` · `number` · `outline` |

`marker` 배치를 가진 슬롯이 **위치를 가진 슬롯**이다. 값뿐 아니라 좌표까지
사용자 편집 대상이고, 이동 범위는 `regionId`가 가리키는 영역이다. 마커 배치는
슬롯당 하나뿐이다 — 두 파트에서 동시에 옮긴다는 건 뜻이 없다.

`tags`는 렌더러가 읽는 자유 표식이다. 축구 게임판은 골키퍼 슬롯에 `goalkeeper`를
단다.

### 윤곽 슬롯 — 사용자 입력에서 생성된 기하 데이터

`outline`은 다른 슬롯과 다르다. **도안이 후보를 미리 선언해 둘 수 없다** — 값이
사용자가 넣은 사진에서 계산돼 나온다(`IDE-019`). `list`도 값을 미리 다 적지는
않지만(직접 더한 도시) 그쪽은 여전히 "고르는 것"이고 이쪽은 "계산되는 것"이다.

```ts
{
  id: 'outline',
  kind: 'outline',
  label: '윤곽선',
  minPoints: 3,
  maxPoints: 2000,
  default: SAMPLE_OUTLINE,          // 사진을 넣기 전에 보일 그림
  placements: [{ partId: 'board', mode: 'control' }],
}
```

- 값은 `[x0, y0, x1, y1, …]`이 **납작하게** 늘어선 배열이고 단위는 **파트 로컬
  mm**다. 마지막 점 다음은 첫 점이라 첫 점을 되풀이해 적지 않는다.
  점마다 객체를 두지 않는 것은 크기 때문이다 — 점 400개가 객체면 12KB, 납작한
  수 배열이면 4KB고 `localStorage`에 들어가야 한다.
- 배치는 `control`뿐이다. 값을 글자나 마커로 그릴 수 없고, 이 값에서 판을 그때
  그리는 것은 파트의 `dynamic`이 한다 — 목록 슬롯과 같은 규약이다.
- **기본값을 비워 두지 않는다.** 사진을 넣기 전에도 카탈로그 썸네일과 소개
  페이지가 그 파트를 그린다. 점 잇기는 앉은 고양이 실루엣을 기본값으로 둔다.
- 에디터는 이 슬롯에 한 줄 입력을 내지 않는다(`SlotField`가 `null`을 준다).
  사진을 넣고 다시 따는 조작은 게임 전용 화면이 맡는다.

**계산 자체는 `src/lib/dot-to-dot/`처럼 순수 함수로 둔다.** DOM에도 서버에도
매지 않아야 브라우저(사진을 다루는 쪽)와 서버 렌더러가 같은 코드를 쓰고,
테스트가 픽셀 배열을 직접 넣을 수 있다.

## 그룹

슬롯을 묶는 단위다. 축구 게임판이라면 팀 하나가 그룹 하나다. 그룹은 자기 이름
슬롯(`text`)과 색 슬롯(`color`)을 가리킬 수 있고, 배치 프리셋의 적용 단위가 된다.

- `mirrorMarkers` — 이 그룹의 마커 아트워크를 세로 중심선 기준으로 뒤집어 그린다.
  방향이 있는 마커를 위한 것이다. 축구 게임판의 마커는 공격 방향을 가리키므로
  (빈 원은 화살촉으로, 선수 그림은 자세로) 반대편으로 공격하는 팀은 뒤집어
  찍는다 — 아트워크 파일을 두 벌 만들지 않는다. **글자는 뒤집지 않는다**
  (등번호는 늘 정방향이다).

## 마커 스타일 변형

같은 슬롯을 여러 모습으로 그리는 장치다. 축구 게임판의 선수 마커가 빈 원 /
선수 그림(실루엣) / 선수 그림(색칠용 윤곽선) 세 벌인 것이 그렇다.

- 기준점은 **마커의 중심**이다. 변형끼리 크기가 달라도 중심이 같으므로 바꿔 끼워도
  배치가 어긋나지 않는다.
- 변형이 둘 이상이면 사용자가 고를 `choice` 슬롯(`selectorSlotId`)이 있어야 하고,
  그 슬롯의 선택지가 변형 id와 **정확히 같아야** 한다. 한쪽만 고치면 검증에서
  걸리므로 둘이 어긋난 채로 남지 않는다.
- 겹침 검사에는 세트에서 가장 큰 변형을 쓴다.

**슬롯마다 다른 그림을 쓰려면 세트를 나눈다.** 아트워크는 변형에, 변형은 세트에
붙으므로 세트 하나로는 슬롯마다 다른 그림을 낼 수 없다. 축구 게임판은 선수 자세를
이렇게 낸다 — 자세마다 세트가 하나씩이고(`player-marker-run` 등), 세트 전부가
같은 변형 구성과 크기를 갖는다. 사용자가 고르는 것은 변형이라 선택 슬롯 하나가
모든 세트를 동시에 바꾼다.

## 배치 프리셋

이름 붙은 슬롯 좌표 집합이다. 전술 대형(4-4-2 등)이 여기 담긴다. 프리셋은
출발점이고, 사용자는 적용한 뒤 **마커를 끌거나 화살표 키로 옮긴다**(`IDE-012`).
어디까지 갈 수 있는지는 슬롯의 `regionId`가 정하고, 그 경계 계산은
[`src/lib/customization/movement.ts`](../src/lib/customization/movement.ts)
한 곳에만 있다 — 화면과 저장 검증이 다른 경계를 쓰면 사용자가 만든 값이
조용히 버려진다.

- 프리셋은 **그룹 하나**를 통째로 배치한다. 두 팀이 서로 다른 대형을 고를 수
  있어야 하므로 하나의 프리셋에 양 팀을 담지 않는다.
- 같은 대형의 팀별 프리셋은 `formationId`로 묶는다. UI는 이 단위로 대형을 보여준다.
  **선택 값이다** — 야구 게임판의 수비 시프트처럼 필드에 서는 그룹이 하나뿐이면
  묶을 팀별 쌍이 없다. 그때 UI는 프리셋의 `label`을 그대로 보여준다.
- 상대 진영용은 `mirrorPositions`로 세로 중심선 기준 반전해 만든다.
- 검증은 이것들을 본다: 그룹의 옮길 수 있는 슬롯을 **빠짐없이 한 번씩** 배치했는가,
  좌표가 영역 안인가, 마커끼리 겹치지 않는가.
- 겹침은 **다른 그룹의 프리셋과도** 본다. 사용자는 그룹마다 프리셋을 따로 고르므로
  (홈 대형 × 원정 대형) 어떤 조합이든 종이 위에서 성립해야 한다. 프리셋 하나
  안의 겹침만 보던 검증은 두 팀을 나란히 놓았을 때를 놓쳤다(`IDE-010`).

> **경기가 되는 배치인지는 검증이 알지 못한다.** 스키마는 "겹치지 않는가"까지만
> 본다. 축구 게임판에서는 두 팀이 각자 진영 절반에 갇히면 상대 골대 쪽에 패스를
> 받을 선수가 없어 경기가 성립하지 않는데, 그 배치도 검증은 통과한다. 게임이
> 성립하는 조건은 도안 쪽 테스트로 지킨다 —
> [`src/assets/games/soccer/__tests__/formations.test.ts`](../src/assets/games/soccer/__tests__/formations.test.ts)와
> [`src/assets/games/baseball/__tests__/artwork.test.ts`](../src/assets/games/baseball/__tests__/artwork.test.ts)가
> 그 예다. 야구 쪽은 "어느 수비 시프트든 외야에 셋, 내야에 여섯"을 본다 —
> 그 조건이 깨지면 한쪽으로 친 타구를 잡을 사람이 없다.

## 표시 규약 — 오림선 · 접는선 · 풀칠면

도안 SVG는 표시를 **정해진 레이어 id** 안에 그린다. 렌더러가 레이어 id로 찾아
스타일을 입히므로 도안 쪽에서 선 굵기·파선을 직접 정하지 않는다. 배율이 바뀌어도
표시선은 굵기를 유지한다 — 200%로 뽑았다고 오림선이 두 배로 굵어지면 자를 자리가
흐려진다.

| 표시            | 레이어 id          | 모양             | 사용자에게 뜻하는 것          |
| --------------- | ------------------ | ---------------- | ----------------------------- |
| `cut`           | `pc-cut`           | 실선 0.25mm      | 따라 자른다                   |
| `fold-mountain` | `pc-fold-mountain` | 일점쇄선 0.2mm   | 인쇄면이 바깥으로 오게 접는다 |
| `fold-valley`   | `pc-fold-valley`   | 파선 0.2mm       | 인쇄면이 안으로 오게 접는다   |
| `glue`          | `pc-glue`          | 가는 파선 0.15mm | 빗금 면에 풀을 발라 붙인다    |

정확한 값은 [`src/lib/schema/marks.ts`](../src/lib/schema/marks.ts)의
`MARK_STYLES`에 있다.

슬롯이 놓이는 자리는 `pc-slot` 레이어로 비워 둔다. **아트워크가 값을 직접 그려
넣지 않는다** — 등번호나 팀 이름을 SVG에 박아 두면 커스터마이즈가 먹지 않는다.
색을 받는 레이어는 슬롯의 `layerId`와 같은 id를 쓴다(예: `pc-team-home`).

## 커스터마이즈 값

사용자가 채운 값은 `GameCustomization` 하나에 담긴다 — 슬롯 값(`values`)과 마커
좌표(`positions`)다. 게임마다 모양이 같으므로 에디터도 저장·복원 코드도 게임을
알 필요가 없다.

- `defaultCustomization(game)` — 도안 기본값으로 채운 첫 상태이자 '되돌리기'의 목적지
- `validateCustomization(game, c)` — 값과 좌표가 제약을 지키는지, 사유와 함께
- `validateSlotValue(slot, value)` — 입력 한 칸 검증. 에디터의 폼이 그대로 쓴다
- `applyPreset(game, c, presetId)` — 프리셋 적용(원본을 건드리지 않는다)
- `resolveVariant(game, styleSetId, c)` — 사용자가 고른 마커 스타일 변형
- `slotsOfPart(game, partId)` — 그 파트에 **배치가 있는** 슬롯
- `slotsAffectingPart(game, partId)` — 그 파트의 인쇄물을 **실제로 바꾸는** 슬롯

뒤의 둘은 다르다. 그룹의 **색 슬롯은 배치가 없는 파트에도 영향을 준다** — 그
그룹의 마커가 그 색으로 칠해지기 때문이다(`groupColorOf`). 축구 게임판의 팀 색은
**배치가 하나도 없는데도** 운동장 선수 마커를 칠한다.

그래서 색 슬롯은 `placements`가 비어도 되는 **유일한 예외**다. 배치도 없고 어느
그룹의 `colorSlotId`도 아닌 슬롯은 `parseGame`이 막는다 — 값이 갈 곳이 없다.

에디터는 뒤의 것을 쓴다. **지금 편집 중인 파트에 쓰이는 옵션만** 보여 주기
때문이다(2026-09-08 사용자 요청) — 운동장에서는 마커 모양·대형·팀 색이 모두
보이고, 점수 기록칸과 골대 전개도에서는 옵션 줄이 통째로 사라진다. 배치만 보고
걸렀다면 운동장을 편집하는 동안 팀 색이 사라졌을 것이다.

## 검증이 잡아 주는 것

`parseGame`은 형식뿐 아니라 도안 안의 관계를 본다. 대표적으로:

- 슬롯이 없거나 · id가 중복이거나 · 값 종류가 틀리거나 · 어느 파트에도 속하지 않음
- 인쇄 방향이 치수와 어긋남
- 보드 파트가 1개가 아님
- 파트 종류에 맞지 않는 표시(보드에 오림선, 조립물에 접는선 없음)
- 좌표가 파트 밖 · 마커 기본 좌표나 프리셋 좌표가 영역 밖
- 프리셋에 슬롯이 빠지거나 중복되거나 마커가 겹침
- 마커 스타일 선택지와 변형 목록이 어긋남
- 자산 경로가 다른 게임을 가리킴
- 스키마에 없는 속성(오타)을 적음
