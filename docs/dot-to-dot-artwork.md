# 점 잇기 도안

`IDE-019`(사진 윤곽선과 점·번호 도안)의 작도 결과다. 치수의 **원본은 코드**
(`src/assets/games/dot-to-dot/dimensions.ts`, `src/lib/dot-to-dot/dots.ts`)이고
이 문서는 왜 그 값이 되었는지를 적는다. 둘이 어긋나면 코드가 맞다.

인쇄 규격은 [`print-spec.md`](print-spec.md), 도안 데이터 모델은
[`game-authoring.md`](game-authoring.md)를 따른다.

앞선 네 게임과 근본이 다른 곳이 하나다 — **인쇄물의 형태가 저장소에 없다.**
축구·야구·세계일주·윷놀이는 도안이 저장소 안에 있고 사용자는 이름·색·마커
자리만 고쳤다. 점 잇기는 판 위의 점과 번호가 **사용자가 넣은 사진**에서 나온다.

---

## 1. 만드는 법

```
src/lib/dot-to-dot/          ← 사진 → 윤곽 → 점. DOM에도 서버에도 매지 않는다
  image.ts                     줄이기 · 회색조+흐리기 · Otsu 이진화
  trace.ts                     marching squares · Chaikin · RDP
  outline.ts                   한 줄로 잇고 실패를 판정한다
  detail.ts                    다단계 임계값으로 피사체 안쪽 선을 딴다
  dots.ts                      점 배분 · 번호 자리 · 개수 상한
  geometry.ts                  닫힌 다각형 도구(호길이·법선·방향)
  browser.ts                   ← 여기만 <canvas>에 매인다. index.ts가 안 내보낸다

src/assets/games/dot-to-dot/
  dimensions.ts              ← 판 치수와 상자, 보기 그림(앉은 고양이)
  rules.ts                   ← 게임 방법 텍스트와 판에 찍는 한 줄
  artwork/
    board.ts                   점 잇기 판 190×277
    answer.ts                  완성 그림 부속 100×146
    dynamic.ts                 값 → 판. 서버 렌더러가 부른다
  index.ts                   ← 도안 정의
public/games/dot-to-dot/*.svg  ← 기본값(보기 그림)으로 그린 산출물. 커밋한다
```

```bash
npm run artwork dot-to-dot   # 이 게임의 SVG만 다시 만든다
npm run test:run             # 커밋된 SVG가 생성기와 같은지까지 본다
```

## 2. 사진은 서버로 가지 않는다

아이 사진이다. 브라우저에서 `<canvas>`로 처리하고 **점 좌표와 번호만 남긴 뒤
사진은 버린다.**

```
ImageData → traceOutline → outline(number[] · 판 좌표 mm) → planDots → SVG
             ↑ 브라우저에서 끝난다        ↑ 서버로 가는 것은 이것뿐이다
```

경계가 `traceOutline`이다. 들어가는 것은 픽셀이고 나오는 것은 좌표뿐이라, 그
뒤로 사진이 흘러갈 길이 코드에 없다. 요청 본문 규격(`customizationBody`)도
글자·수·좌표만 받으므로 데이터 URL이 낄 자리가 없고, 도안 테스트가 그것을
확인한다.

PDF를 서버에서 만드는 이유(4.4MB 한글 폰트, [`print-spec.md`](print-spec.md) §3)와
충돌하지 않는다. 점 100개의 좌표는 몇 킬로바이트고, 서버는 그것만 받아 지금과
같은 방식으로 PDF를 만든다.

**외부 라이브러리를 들이지 않았다.** OpenCV.js는 8MB가 넘어 이 사이트가 여는 첫
화면보다 크다. 아래 파이프라인은 전부 직접 구현할 수 있는 크기였다.

## 3. 윤곽 따기 — 여섯 단계

| 단계          | 함수                            | 왜                                    |
| ------------- | ------------------------------- | ------------------------------------- |
| 줄이기        | `downscale` (긴 변 1024px)      | 노이즈가 줄고 뒤 단계가 전부 빨라진다 |
| 회색조·흐리기 | `toGray` · `gaussianBlur`(σ1.4) | 옷의 무늬 같은 잔결을 없앤다          |
| 이진화        | `otsuThreshold` · `binarize`    | 피사체와 배경을 가른다                |
| 윤곽 추적     | `traceContours`                 | marching squares로 등고선을 딴다      |
| 다듬기        | `chaikin` (한 판)               | 화소 경계의 계단을 깎는다             |
| 단순화        | `simplify` (RDP)                | 남는 점이 곧 **형태의 모서리**다      |

세 군데에 이유가 붙는다.

**어느 쪽이 피사체인가는 밝기가 아니라 테두리가 정한다.** 밝은 배경에 어두운
아이도, 어두운 배경에 밝은 아이도 있다. `binarize`는 사진 가장자리를 절반 넘게
차지한 쪽을 배경으로 보고 필요하면 뒤집는다. 이 뒤집기가 없으면 어두운 배경에
밝게 선 아이가 통째로 배경이 된다.

**Chaikin은 한 번만 돌린다.** 두 번 이상 돌리면 강아지 귀 끝처럼 실제로 뾰족한
자리까지 둥글어져, 뒤이은 점 배분이 집을 모서리가 사라진다.

**RDP는 무게중심에서 가장 먼 점에서 시작한다.** 닫힌 도형은 "어디서 시작하는가"
가 없어 그냥 돌리면 0번 점이 그저 배열의 첫 칸이라는 이유로 살아남는다. 가장 먼
점은 형태의 뾰족한 끝(귀·꼬리)일 가능성이 높아 시작점으로 알맞다.

단순화 세기는 윤곽 대각선의 **0.4%**다(`SIMPLIFY_RATIO`). 화소 크기와 무관해져
사진을 크게 넣든 작게 넣든 남는 꼭짓점 수가 비슷하다.

### 실패를 조용히 넘기지 않는다

빈 판이 나오고 마는 것이 제일 나쁘다. `traceOutline`은 성공하면 좌표를, 실패하면
**사유와 한국어 한 줄**을 돌려준다.

| `reason`    | 판정                                          | 무엇이 잘못된 사진인가    |
| ----------- | --------------------------------------------- | ------------------------- |
| `empty`     | 고리가 없거나 꼭짓점 8개 미만                 | 단색에 가까운 사진        |
| `too-small` | 가장 큰 고리가 사진 넓이의 4% 미만            | 피사체가 멀다             |
| `flooded`   | 92%를 넘는다                                  | 역광 · 배경과 밝기가 비슷 |
| `scattered` | 큰 조각이 6개 초과, 또는 1등의 몫이 절반 미만 | 배경이 복잡하다           |

`scattered`가 두 잣대를 함께 보는 것은 둘이 다른 실패를 잡기 때문이다 — 몫은
"비등한 덩어리 둘"을, 조각 수는 "잘게 흩어진 배경"을 잡는다.

이 사유를 "무엇을 하면 되는지"로 옮겨 적는 것과 임계값을 사용자가 미는 것은
`IDE-020`이 했다. 슬라이더는 **절대값이 아니라 Otsu에서 민 정도**를 준다
(`thresholdOffset`, ±60) — 절대값을 걸면 사진마다 쓸 만한 구간이 달라 같은
손놀림이 다른 결과를 낸다. 실패해도 **값은 건드리지 않는다**: 직전 그림이나
보기 그림이 판에 그대로 남아 종이가 비지 않는다.

## 4. 점 배분 — 모서리 먼저

**호길이를 N등분해 찍으면 형태가 뭉개진다.** 뾰족한 모서리가 두 점 사이에
묻히기 때문이다. 강아지 귀 끝이 점을 못 받으면 다 이어도 귀가 나오지 않는다.

1. **모서리 먼저.** 단순화가 남긴 꼭짓점을 꺾인 각(라디안 0.3 = 약 17° 이상)이
   큰 순으로 집는다. 이때도 **간격을 지킨다** — 꼭짓점 둘이 1mm 사이로 붙어 있는
   자리에서 둘 다 집으면 번호 두 개가 겹쳐 앉는다.
2. **나머지를 호길이 균등으로.** 가장 넓게 벌어진 사이를 반으로 가르기를
   되풀이한다. 긴 직선 구간이 점 없이 비지 않는다.
3. 모서리가 N보다 많으면 꺾인 각이 큰 것부터 N개다.

### 개수 상한

**입력한 개수를 지킨다.** 30을 넣으면 정확히 30개다. 다만 상한이 있다 —

```
상한 = ⌊둘레 ÷ 최소 간격(8mm)⌋
```

넘으면 상한에서 멈추고 `clamped`·`capacity`로 그 사실을 함께 돌려준다. 조용히
줄이지 않는다.

**슬롯의 최대치 100은 둘레가 800mm를 넘는 윤곽에서만 다 들어간다.** 판 안쪽
상자(144×208)에 들어가는 볼록한 도형의 둘레는 최대 704mm이므로, 사람이나 인형
처럼 대체로 볼록한 피사체는 80대 후반에서 걸린다. 보기 그림(앉은 고양이)이 86
이다. 만 6세 목표인 50은 넉넉히 들어간다. 최소 간격 8mm는 실측으로 정할 값이라,
종이 실험에서 6mm로 줄면 상한이 118로 오른다.

## 5. 번호

**점 위가 아니라 점 옆이다.** 요청 문구는 "점 위에 숫자"였지만(2026-09-08) 겹쳐
찍으면 연필을 댈 표적이 가려진다. **윤곽선의 법선 방향 바깥쪽**에 놓아 도안
안쪽을 비운다 — 아이가 그을 선이 지나갈 자리다.

- **1번은 가장 위쪽 점**, 진행은 **시계 방향**이다. 저장된 윤곽의 방향이 어느
  쪽이든 `planDots`가 시계로 맞추므로, 다시 연 도안도 같은 차례로 번호가 붙는다.
- 시작점 옆에 **화살촉**이 1번에서 2번 쪽을 보고 앉는다. 두 점의 가운데가 아니라
  **1번에서 잰 거리**로 놓는다 — 점이 성길 때 가운데에 두면 1번에서 20mm나
  떨어져 무엇을 가리키는지 알 수 없다.
- 닫힌 윤곽이라 마지막 점은 1번으로 돌아온다. **"1로"**를 적지 않으면 아이가
  거기서 멈춘다.

### 겹침 회피 — 바깥으로, 안 되면 옆으로

바깥으로만 밀면 **오목한 자리에서 오히려 더 겹친다.** 고양이의 두 귀 사이나
목처럼 윤곽이 안으로 굽은 곳에서는 바깥 법선이 한 점으로 모이기 때문이다.

그래서 후보 자리를 **바깥 거리 × 진행 방향 거리**의 격자로 두고, 제 점에서
멀어지는 정도가 작은 것부터 쓴다(`LABEL_SPOTS`). 번호가 제 점에서 멀면 어느
점의 번호인지 헷갈리므로, 겹침을 피하는 것보다 가까이 두는 것이 먼저다. 격자를
다 써도 못 피하면 마지막 자리를 쓰고 `crowded`로 알린다 — 번호를 아예 빼면
아이가 셀 수를 잃는다.

번호는 `ART_AREA` 안으로 붙들려 종이 밖으로 나가지 않는다.

## 6. 판

**190×277mm 세로 한 장**이다. A4 세로(210×297)에서 가정용 프린터의 인쇄 여백을
뺀 크기다.

```
y=14   제목(사용자 값) · y=20 제목 밑줄 — 비우면 손으로 쓴다
y=27.5 "1번부터 번호를 차례로 이어 보세요."
       ┌──────────────────────────────┐ ART_AREA  12,33 · 166×230  (번호가 갈 수 있는 데까지)
       │  ┌────────────────────────┐  │ OUTLINE_BOX 23,44 · 144×208 (윤곽선이 앉는 상자)
       │  │                        │  │
       │  └────────────────────────┘  │
       └──────────────────────────────┘
y=269  "다 이으면 색칠해 보세요."
```

두 상자의 차이 **11mm**(`LABEL_REACH_MM`)가 번호가 밀려날 폭이다. 윤곽을 판
끝까지 채우면 번호가 갈 자리가 없다.

**보드 파트는 정확히 1개**여야 하므로(`parseGame`) 가로 사진이 들어와도 이 판을
쓴다. 윤곽선을 비율 그대로 맞춰 넣고 남는 쪽을 비운다 — 늘여 맞추면 아이 얼굴이
길어진다. 사진을 90°씩 돌리고 좌우로 뒤집는 것은 `IDE-020`이 냈고, **각도를 값으로
들고 다니지 않고 사진을 다시 구워** 저장한다 — 그 뒤로는 윤곽을 다시 딸 때도
사진을 판 위에 겹쳐 볼 때도 "지금 몇 도인가"를 아무도 묻지 않는다.

### 완성 그림 (`answer`, 100×146)

다 이었을 때 나오는 실루엣이다. **어른이 먼저 보는 종이**로, 사진에서 윤곽을
제대로 땄는지 뽑기 전에 확인하는 용도다. 아이에게 먼저 보이면 놀이가 끝나므로
판에 얹지 않고 따로 뽑는 파트로 뗐다.

판과 **같은 가로세로비**(190:277 ≈ 100:146)라, 다 이은 판 위에 겹쳐 보면 같은
모양이 나와야 한다. 값은 판 좌표로 저장돼 있으므로 부속 상자
(`ANSWER_BOX`)에 **다시 맞춰** 그린다 — 그냥 축소하면 판의 빈 여백까지 함께
줄어들어 실루엣이 종이 가운데를 벗어난다.

## 7. 실측으로 정할 값

종이에 뽑아 아이가 실제로 그어 봐야 정해진다. 아래는 **출발점**이다
(`DOT_METRICS` · `dimensions.ts`).

| 값             | 출발값   | 무엇으로 정하나                            |
| -------------- | -------- | ------------------------------------------ |
| 점 지름        | 1.8mm    | 연필 끝을 대기에 충분하고 선에 묻히지 않게 |
| 번호 글자 크기 | 3.2mm    | 만 4세가 혼자 읽는 최소 크기               |
| 최소 점 간격   | 8mm      | 점과 점 사이를 한 획으로 긋는 거리         |
| 안내선 농도    | 15% 회색 | 보고 따라 그을 수 있되 답이 되지는 않게    |

판의 배율 하한 `0.8`은 번호 글자가 정한다 — 3.2mm × 0.8 = 2.56mm이고, 그 아래는
만 4세가 못 읽는다.

## 8. 슬롯

| 슬롯         | 종류      | 값                                      |
| ------------ | --------- | --------------------------------------- |
| `title`      | `text`    | 도안 제목. 판 위쪽과 완성 그림에 찍힌다 |
| `dot-count`  | `number`  | 5~100, 정수. 기본 20                    |
| `guide-line` | `choice`  | 안내선 없음 / 옅은 안내선. 기본 없음    |
| `outline`    | `outline` | 사진에서 딴 닫힌 폴리라인(판 좌표 mm)   |
| `detail`     | `outline` | 미리 그려 두는 세부 선. 고리 여럿       |

`guide-line`은 나이를 가른다. 만 3~4세는 옅은 윤곽선이 있어야 선을 따라가고, 그
위 나이는 없어야 놀이가 된다.

`outline`은 **이 게임이 규격에 더한 슬롯 종류**다. 자세한 것은
[`game-authoring.md`](game-authoring.md)의 「윤곽 슬롯」 절에 있다.

`dot-count`가 `number` 슬롯에 `control` 배치를 쓴 첫 자리다 — 값이 글자로 찍히는
게 아니라 판 전체를 다시 그리게 한다.

## 8-1. 세부 선 (IDE-021)

윤곽선만 따면 다 이어도 **실루엣 하나**가 남아 무엇을 찍은 사진인지 알아보기
어렵다(2026-09-09 사용자). 눈·입·머리카락 경계는 임계값이 하나뿐이라 안 나온다
— 얼굴도 머리도 눈도 전부 마스크 `1`로 뭉쳐 고리가 아예 생기지 않는다.

**밝기를 여러 단으로 나눠 각 단의 경계를 딴다**(`src/lib/dot-to-dot/detail.ts`).

1. 피사체 마스크를 **짧은 변의 1.2%만큼 깎는다**(erode). 깎지 않으면 머리카락
   경계처럼 실루엣에 딱 붙은 고리가 나와, 점을 잇기도 전에 답이 종이에 보인다.
2. 깎은 안쪽 화소의 밝기만으로 히스토그램을 만들고 **가장 잘 갈리는 단을 골라
   다시 가르기**를 되풀이한다(사용자가 고른 단 수만큼, 최대 3).
3. 단마다 `gray <= t`인 자리를 마스크로 만들어 `traceContours` → Chaikin → RDP.
4. **거른다** — 잔티(피사체 넓이의 0.5% 미만), 실루엣을 되짚는 고리(60% 초과),
   같은 경계를 두 번 딴 고리. 남은 것을 큰 것부터 담되 **고리 10개 · 점 800개**
   예산 안에서 멈춘다.

**세부에는 점도 번호도 붙지 않는다.** 아이가 잇는 선은 여전히 윤곽 하나뿐이라
연필을 뗄 자리가 없다 — 획을 나누면 "여기서 떼세요"를 도안에 표시하는 방법부터
정해야 하고, 그건 이 놀이를 처음 하는 나이대에 이르다(IDE-021 결정).

굵기는 **0.45mm**로 윤곽선(답, 0.9mm)보다 가늘다. 그림의 일부로 보이되 아이가
이을 선과 헷갈리지 않아야 한다.

세부는 **윤곽과 같은 변환으로** 판에 앉는다. 따로 맞춰 넣으면 눈이 종이를 가득
채운다 — `fitTransform`을 한 번 구해 윤곽·세부·(대조 보기의) 사진에 함께 먹인다.

세부를 몇 단으로 딸지는 **슬롯이 아니라 사진 기록에 남는다** — 밝기 밀기와 같은
"어떻게 뽑았나" 설정이다(`StoredPhoto.detailLevel`, IDE-020).

## 9. 보기 그림 — 앉은 고양이

사진을 넣기 전의 기본값이자 카탈로그 썸네일이다. 빈 판을 기본값으로 두면 소개
페이지에 아무것도 없는 종이가 걸리고, 사진을 넣기 전에는 이 놀이가 무엇인지
보이지 않는다.

몸과 머리는 좌우 대칭이라 **오른쪽 절반만 적고 뒤집어 잇는다.** 손으로 적은
좌표가 스무 쌍이면 한쪽이 어긋나도 눈에 안 띄는데, 뒤집어 만들면 그럴 수가 없다.
**꼬리만 뒤집지 않는다** — 대칭에 함께 태우면 꼬리가 양쪽에 하나씩 달려 고양이가
아니라 날개 달린 무엇이 된다.

귀 끝 둘과 꼬리 끝이 뾰족해 **모서리 먼저** 규칙이 실제로 걸린다. 도안 테스트가
점 스물을 찍어 그 셋이 점을 받는지 본다.

**눈 둘과 코 하나**가 세부 선으로 붙어 있다(IDE-021). 실루엣만 있으면 소개
페이지에서 고양이인지 무엇인지 알 수 없다. 몸통과 **같은 변환**으로 앉히므로
얼굴이 제자리에 온다 — 각각 따로 맞춰 넣으면 눈이 판을 가득 채운다.

썸네일이 성기게 보이는 것은 기본값이 점 스물이기 때문이고, 그것이 만들기 화면을
열었을 때 실제로 나오는 종이다. 썸네일에 점을 더 찍으면 기본값을 모르는 곳
(카탈로그·소개 페이지)이 보는 그림과 실제 첫 화면이 어긋난다.

## 10. 안 한 것

- **세부 선을 아이가 잇게 하는 것.** 눈·입 같은 선은 `IDE-021`이 판에 그리게
  됐지만 **점도 번호도 붙지 않는다.** 선을 떼었다 다시 시작하는 것은 이 놀이를
  처음 하는 아이에게 어렵고, 도안에 "여기서 연필을 떼라"를 표시하는 방법부터
  정해야 한다. 실물로 놀아 본 뒤에 판단한다.
- **사진을 인쇄물에 넣는 것.** 파서가 `<image>`를 모르기도 하지만, 그보다 이을
  선이 이미 종이에 보이면 아이가 번호를 따라갈 이유가 없어진다.
- **사진을 서버에 저장하는 것.** 다시 편집하려면 사진이 필요한데, `IDE-020`은
  그것을 **브라우저 안**에 두기로 했다 — 긴 변 512px JPEG 한 장이 커스터마이즈와
  다른 `localStorage` 키에 남는다. 서버로 가는 것은 여전히 좌표뿐이다.
